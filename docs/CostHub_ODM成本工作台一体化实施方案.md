# CostHub ODM 成本工作台一体化实施方案

> 状态：待实施  
> 实施对象：CostHub 2.3.x（Tauri + React + TypeScript + SQLite）  
> 目标：将现有分散功能串成适合真实 ODM 项目的成本工作主线，并保留历史项目作为可复用成本基线。

## 1. 产品结论

CostHub 不应变成替代成本人员的自动化黑箱，也不应继续增加彼此割裂的分析入口。产品应定位为：

**ODM 成本决策工作台 = 项目成本档案 + AI 成本参谋 + 可追溯证据库。**

人的职责是确认业务口径、模块边界、目标与谈判策略；程序负责可靠计算、版本差异、数据校验和批量处理；AI 负责发现遗漏、解释变化、提出问题和生成下一步建议。

本方案遵循以下边界：

- 不建设采购订单、库存、合同、付款等 ERP 功能。
- 不复制财经损益系统；只记录财经结论、目标边界、附件与版本。
- 不要求 AI 自动决定器件模块归属。
- 不允许云端模型成为成本计算的唯一执行者。
- 不推倒现有项目、招标、供应商、分析成果和工作手账；优先复用并串联。
- 不增加新的前端依赖，优先使用现有 Ant Design、ECharts、React Flow、XLSX 和 CSS。

## 2. 真实业务主线

```text
领导讨论目标 + 财经损益结论
              ↓
          目标基线
              ↓
ODM资源池筛选 → 标前摸底交流
              ↓
首轮报价 → 找低价项/异常项 → 指导供应商降本
              ↓                         ↑
第二轮、第三轮报价 ─────────────────────┘
              ↓
正式招标 → 定点供应商
              ↓
OpenBOM V1.0 定稿
              ↓
量产前局部变更 → OpenBOM V1.1
              ↓
量产项目持续降本机会
              ↓
项目复盘 / 管理汇报 / 工作手账 / 绩效素材
```

项目页必须明确回答：当前阶段、目标差距、关键机会、数据缺口、风险和下一步行动。

## 3. 信息架构与项目类型

### 3.1 顶层导航

不再新增孤立入口。沿用现有整体导航，并把能力收敛为以下使用心智：

- 驾驶舱：项目组合、目标差距、待处理机会、近期变化。
- 项目管理：每个项目的完整成本档案与阶段主线。
- 物料与供应商：器件库、模块库、ODM 资源池、物料洞察。
- 分析成果：由 AI 或规则生成、可保存和复用的分析成果。
- 工作手账：独立页面，记录经历、心得、行动、复盘和绩效素材。
- AI 协作：右侧常驻入口；可全屏，但结果必须可保存到相应业务对象。

### 3.2 两种项目录入方式

创建项目时提供两个清晰选项，仍写入现有项目体系，不另建“历史项目系统”：

1. **在研 ODM 项目**：走目标、摸底、报价、招标、定点、OpenBOM、量产变更和复盘完整流程。
2. **历史成本基线**：直接录入项目规格、供应商、价格日期和最终 OpenBOM；不强制补录过去不存在的报价轮次、谈价和过程记录。

历史项目导入完成后显示“历史基线”标签，可参与相似项目、模块成本和物料价格比较。历史项目可以补充多个 OpenBOM 版本，但默认只需一次整理。

历史基线必须保存：

- 项目代号、名称、定位、关键规格、量产或定稿时间。
- ODM 供应商、币种、税制和价格日期。
- 原始 OpenBOM 文件名与文件哈希。
- 模块、物料、型号、规格、数量、单价、小计。
- 定稿成本、版本、数据来源与数据完整度。

可信度分为“正式定稿”“正式报价但不完整”“估算/早期摸底”。AI 与比价默认优先使用正式定稿数据，并在引用低可信基线时明确提示。

## 4. 项目成本驾驶舱

项目详情顶部改造成稳定的项目成本驾驶舱，不通过新增更多平级页签堆功能。

### 4.1 顶部阶段条

在研项目阶段：

```text
立项目标 → 资源池摸底 → 多轮报价 → 招标定点 → OpenBOM定稿 → 量产前变更 → 量产降本 → 复盘
```

历史基线项目阶段简化为：

```text
项目资料 → OpenBOM整理 → 基线冻结
```

阶段条只表达真实顺序。当前阶段高亮；完成阶段显示可回看的产物数量；存在阻塞时显示红点和具体原因。阶段切换不能静默改写数据。

### 4.2 项目首屏

首屏固定呈现：

- 当前 BOM/最新报价与目标的差额。
- 当前阶段及下一步。
- 三条最重要的成本机会或风险。
- 待确认数据数量、未归类器件数量、待跟进议价项。
- 最新一次报价、BOM 或目标变化。

AI 摘要必须使用结构化卡片，而非一段不可操作的长文本。每条建议包含：

- 结论。
- 依据与可追溯来源。
- 预计影响金额或区间。
- 置信度和数据缺口。
- 下一步动作、负责人、截止时间。
- “加入议价清单”“保存成果”“记录手账”等明确动作。

## 5. 目标基线

现有 `project_targets` 保留为模块/领域目标编辑数据。新增轻量的目标基线元数据与冻结能力，不重做计算公式。

目标基线至少包括：

- 版本号与状态：草稿、已确认、已作废。
- BOM 总目标和整机边界。
- 领导确认结论。
- 财经损益结论或附件说明。
- 模块目标快照。
- 关键假设、确认人、生效日期和备注。

冻结目标时保存当时模块目标 JSON 快照，后续修改生成新版本，不覆盖历史。项目报价轮次和 OpenBOM 版本均可选择其对比的目标版本。

成本目标不是 AI 自动生成的最终答案。AI 只能参考历史项目和规格给出区间、拆分建议及依据，最终由用户确认。

## 6. ODM 资源池、报价和议价闭环

### 6.1 ODM 资源池

复用 `supplier_profiles` 和 `project_suppliers`，补足项目过程需要的最小字段：

- 优势品类、覆盖产品档位、典型项目。
- 联系与响应情况、历史报价竞争力、质量/技术备注。
- 项目内状态：候选、已接触、已摸底、已报价、入围、参标、中标、备选、未选。

不做复杂自动评分。首期只显示已有数据与简单可解释指标，例如历史中标次数、平均报价排名和响应记录。

### 6.2 多轮报价

复用现有 `project_spec_baselines`、`tender_rounds`、`supplier_quote_batches`、`supplier_quote_lines` 和 `quote_line_matches`。

矩阵必须同时表达：

- 当前轮各供应商报价。
- 相对目标、历史基线和本轮最低价的差距。
- 相比上一轮的降幅。
- 规格是否可比、缺失项和异常口径。
- 理论组合低价明确标注为“谈判锚点”，不得描述为实际采购方案。

### 6.3 议价机会台账

复用并扩展现有 `negotiation_items`，避免再建一套“AI建议表”。至少补充：

- 机会来源、当前报价、基准价、目标价。
- 预计节省、已确认节省、已实现节省。
- 供应商反馈、下一步动作、负责人、截止时间。
- 状态：待评估、待沟通、沟通中、供应商接受、已落地、关闭。
- 证据引用和置信度。

“发现机会”“供应商接受”“OpenBOM 已体现”必须是不同状态，不能把建议金额直接计入已实现降本。

## 7. OpenBOM 导入与模块整理台

这是本方案的核心工程能力。

### 7.1 原则

- 供应商原始文件先进入持久化整理区，不直接覆盖正式项目 BOM。
- 模块归属属于项目 BOM 行，不作为器件库中器件的全局固定属性。
- AI 或规则只可建议模块，不可在低置信度时静默决定。
- 首次 OpenBOM 允许人工批量归类；后续版本只处理新增和变化行。

### 7.2 导入双通道

1. **标准模板**：最快、最准，适合正式历史基线和定稿 OpenBOM。
2. **供应商原始文件**：自动探测表头并进入字段映射预览；用户确认后记住该供应商格式。

标准 BOM/报价模板统一使用，不为每个流程制造新模板。建议字段：项目代号、数据类型、供应商、报价轮次、BOM版本、价格日期、币种、税制、模块、物料类别、物料名称、型号、规格、数量、单价、小计、备注。

字段映射配置按“供应商 + 表头签名 + 文件类型”保存。列名变化或识别置信度不足时重新预览，不直接套用旧映射。

### 7.3 整理台布局

使用稳定三段式工作区，背景保持实色或高不透明度，不使用影响阅读的全屏玻璃透明叠层：

```text
┌──────────────────────────────────────────────────────────────────────┐
│ OpenBOM V1.0 · 286 行    未归类 42    异常 6    金额 ¥742.30        │
├───────────────────────────────┬──────────────────────────────────────┤
│ 器件表格                      │ 项目模块树 / 成本结构                 │
│ □ 名称  型号  数量  单价      │ ├─ 显示模块 ¥420  56.6%             │
│ □ ...                         │ ├─ 主控模块 ¥126  17.0%             │
│                               │ ├─ 电源模块 ¥82   11.0%             │
│ [批量归类] [批量修改]         │ └─ 未归类   ¥32    4.3%             │
├───────────────────────────────┴──────────────────────────────────────┤
│ 版本差异 / 校验问题 / 原始行依据                                    │
└──────────────────────────────────────────────────────────────────────┘
```

左侧主表支持筛选：全部、未归类、待确认、异常、新增、删除、价格变化、数量变化。右侧模块树展示模块金额、占比、目标差额和未归类数；点击模块过滤器件，不能只作为装饰图。

### 7.4 模块建议与继承顺序

按以下确定性顺序匹配，先规则后 AI：

1. 同项目上一正式版本相同来源行标识。
2. 同项目相同型号 + 物料名称。
3. 当前项目已人工确认的映射。
4. 相似历史项目中一致归属的建议。
5. 名称关键词或本地模型建议。
6. 存在冲突、无历史或置信度不足时保持“未归类”。

界面必须区分“自动继承”“规则建议”“AI建议”“人工确认”。只有人工确认或高可信同项目继承可直接用于冻结，其他建议可一键批量接受但必须可撤销。

### 7.5 全局多选与批量处理规范

任何可能超过 10 行的列表都必须评估批量操作。以下页面必须提供多选：

- OpenBOM 整理台。
- 项目 BOM。
- 报价矩阵待确认项。
- 议价机会台账。
- 历史基线项目列表。
- AI 待处理建议或数据质量问题。

统一交互要求：

- 表头全选当前筛选结果；清楚区分“本页全选”和“全部结果全选”。
- 选中后出现粘性批量操作条，显示选中数量和金额合计。
- 支持 Shift 连选、跨页选择、取消选择和 Esc 清空。
- BOM 整理台支持批量归入模块、批量新建模块并归入、批量修改数量/单价/分类、批量忽略建议、批量恢复。
- 破坏性操作必须二次确认；操作后提供可撤销入口或可恢复记录。
- 批量操作应使用数据库事务，失败时整体回滚并给出具体失败原因。
- 禁止循环逐行弹提示；完成后只显示一次汇总结果。
- 批量操作不能阻塞界面；超过 500 行时显示进度和最终成功/失败数量。

### 7.6 OpenBOM 正式版本

成本快照继续用于日常变化提醒，但不能替代正式 OpenBOM 版本。新增不可变版本表：

- `project_bom_versions`：项目、版本号、版本类型、来源文件、文件哈希、供应商、价格日期、币种、税制、目标版本、状态、变更原因、创建时间。
- `project_bom_version_lines`：版本内完整行快照，包含模块、物料、型号、规格、分类、数量、单价、小计、来源行和原始 JSON。

冻结 V1.0 时复制整理完成的全部行。V1.1 导入后生成与 V1.0 的明确差异：新增、删除、替换、数量变化、价格变化、模块变化及成本影响。旧版本永不覆盖。

正式版本冻结后，可选择同步为当前 `project_boms`，但必须在同一事务内完成，并记录来源版本。失败则整体回滚。

### 7.7 建议的最小新增数据

优先复用现有表，只新增真正无法由现有表表达的数据：

- `project_target_baselines`：目标版本元数据与模块目标快照。
- `bom_import_batches`：持久化导入整理任务和字段映射结果。
- `bom_import_rows`：整理区标准化行、建议、确认状态和原始数据。
- `import_mapping_profiles`：供应商文件字段映射配置。
- `project_bom_versions`、`project_bom_version_lines`：正式不可变 BOM 版本。

已有表采用补列方式扩展；所有 schema 变更沿用 `ensureSchema` 的幂等迁移方式，并为旧数据库提供默认值和索引。

## 8. 量产降本、AI 与成果沉淀

### 8.1 量产降本机会

将物料趋势与正式 BOM 版本关联，按以下可解释规则生成候选机会：

- 当前价格高于同型号或同规格历史低位。
- 物料趋势明显下行但项目价格长期未更新。
- 相似量产项目存在更低方案。
- 同一供应商新项目报价已低于旧量产项目。
- 距上次谈价时间较长且影响金额较大。

机会按“预计影响金额 × 证据可信度”排序，展示项目、模块、物料、为什么现在值得谈、参考依据和建议动作。规则在本地计算；AI 只负责解释与补充问题。

### 8.2 AI 成本参谋

项目打开后，AI 默认检查：

- 目标差距。
- 跨供应商差异。
- 跨项目历史基线。
- 报价轮次变化。
- 规格与成本匹配。
- 数据缺口与口径风险。

AI 不直接写正式 BOM、目标或定点决策。任何建议转成业务数据时使用明确按钮，并保留来源。

### 8.3 分析成果与工作手账

- 分析成果保存可视化结论、证据、筛选条件和当时数据版本。
- 工作手账保持独立页面，不混入分析成果。
- 项目事件、议价行动和 OpenBOM 变更可一键引用到手账。
- AI 可按周、月、季度总结经历、心得、关键贡献、降本结果、未完成事项和绩效素材。
- 自动总结必须区分“已实现结果”和“计划/机会”，避免夸大绩效。

## 9. 云端安全重构

### 9.1 问题

当前前端授权记录、精确 payload 哈希、Rust 二次哈希和正文敏感词扫描相互叠加。动态提示词轻微变化就会导致授权失效；受控模式又拦截数字以及项目、型号、规格、供应商、BOM、成本、价格和报价等正常业务词，造成云端模型实际不可用。

### 9.2 三类数据模式

1. **本地机密**：完整项目、供应商、BOM、报价数据，只给本地模型，无需云端授权。
2. **公共情报**：物料类别、公开型号、行业问题和搜索关键词。用户可按供应商/会话授权，不再绑定每条精确提示词哈希。
3. **受控云端分析**：默认隐藏项目名和供应商名，但允许发送汇总金额、差额、比例和价格区间；调用前展示真实出站预览，可授权本次或当前会话。

### 9.3 实现要求

- Rust 作为唯一授权与网络出口；前端不重复计算授权哈希。
- payload 哈希只用于一次敏感请求的防篡改证据，不作为公共情报的日常授权键。
- 保留 HTTPS、域名白名单、出站预览、大小/超时限制和审计日志。
- 连接测试走固定专用路径，不伪造业务主题授权。
- 错误明确区分策略拦截、授权过期、网络/TLS/代理、超时、API Key 和供应商 HTTP 错误。
- API Key 从 SQLite 明文字段迁移到 Windows 凭据或系统安全存储；迁移成功后清空旧明文。迁移失败不得删除旧值，并给出可恢复提示。
- 云端不可用时，本地规则计算和本地模型功能必须继续工作。

## 10. 视觉、图表与动效规范

### 10.1 视觉方向

继续使用现有 CostHub 的浅色、冷静、轻玻璃质感和主题系统，不另造一套视觉品牌。设计重点是提高信息层级与数据可读性：

- 主工作区使用高不透明度实体表面；全屏模式禁止透出背后页面造成重影。
- 玻璃效果只用于导航或轻量浮层，不能覆盖密集表格和图表。
- 颜色必须表达业务语义：蓝色表示基准/当前，绿色表示达成或降本，橙色表示待确认，红色表示超目标/风险，灰色表示不可比或未分类。
- 金额统一使用等宽数字、右对齐，并保持币种和小数精度一致。
- 文字、标签和空状态使用业务语言，不暴露数据库或模型内部术语。

### 10.2 图表

图表只在能比表格更快表达关系时出现，并必须与明细联动：

- 目标与实际：子弹图或差额条，不使用无意义仪表盘。
- 多轮报价：同一供应商折线 + 目标基准线，突出每轮降幅。
- 模块成本结构：排序横向条形图；模块多时不使用难读饼图。
- OpenBOM 版本差异：瀑布图表达增减成本，同时配套差异明细。
- 供应商横向比价：点图/区间图表达最低、当前和目标，避免堆叠大量柱形。
- 项目组合：目标差额与机会金额采用二维散点或排序条形，必须提供筛选与明细下钻。

所有 ECharts 图表要求：

- 使用现有主题变量，浅色/深色均可读。
- Tooltip 显示口径、版本、时间和来源。
- 数值轴从合理基线开始；截断轴必须明确。
- 标签避免重叠，图例不遮挡数据。
- 空数据、加载、异常状态不显示空白画布。
- 图表点击能过滤或定位对应表格行。
- 导出图片保持清晰，适合汇报使用。

### 10.3 动效

动效只用于反馈、状态指示和空间连续性：

- 模块归类后，行以 160–200ms `transform + opacity` 过渡到新状态；禁止长距离飞行动画。
- 阶段切换、抽屉、弹窗使用 200–250ms 强 `ease-out`。
- 图表数据更新允许 250ms 左右过渡，不能让数值反复跳动。
- 批量操作完成时只对汇总数字和状态标签做一次短促反馈。
- 高频表格选择、键盘操作和逐行编辑即时响应，不添加动画。
- 禁止 `transition: all`、`ease-in`、`scale(0)` 和超过 300ms 的常规 UI 动画。
- 使用 `transform`、`opacity`，避免动画 width/height/margin/top/left。
- 必须兼容现有动效开关和 `prefers-reduced-motion`；关闭动效不能再次破坏 Modal、Select、Popover 可见性。

## 15. 物料洞察工作流补充设计

### 15.1 当前问题与根因

现有物料洞察同时混合了四种对象：快捷洞察物料、器件库关注物料、分解树顶层对象、分解节点生成的行情 `trend_item`。分析成果页又直接枚举 `trend_items`，导致一个复杂物料分解后，叶子节点也被当成独立洞察对象放进总列表。与此同时，原 `Decomposition` 页面不在主导航中，用户从分析成果页只能看到结果，缺少明确的“发起洞察”入口。

必须建立以下层级，禁止继续用筛选掩盖对象混乱：

```text
物料洞察任务（总列表只显示这一层）
├─ 整体洞察结果
├─ 分解树（可选）
│  ├─ 结构节点
│  └─ 叶子节点行情结果
├─ 证据与历史快照
└─ 项目影响与行动建议
```

直接洞察是一条没有分解树的任务；分解洞察是一条包含多个节点结果的任务。两者在总列表中都只占一行/一张卡片。

### 15.2 页面职责

明确区分两个页面职责：

- **物料洞察工作区**：发起、分解预览、选择节点、运行、暂停、重试和查看当前结果。
- **分析成果 > 物料洞察**：查看已经形成的父级成果、收藏、归档、继续追问，不承担复杂执行操作。

复用现有 `Decomposition.tsx` 的解析、节点编辑、批量洞察和快照能力，将其重构为工作区，不再把快捷物料、关注物料和顶层树分成三个不断增长的卡片区。

### 15.3 统一发起入口

分析成果的“物料洞察”页顶部必须有醒目的主入口：

```text
┌────────────────────────────────────────────────────────────┐
│ [直接洞察] [分解型洞察]                                    │
│ 想洞察什么？                                               │
│ [例如：27英寸QHD面板近期是否有降价空间________________]    │
│ [关联项目/物料 可选]                       [开始洞察]       │
└────────────────────────────────────────────────────────────┘
```

入口必须显式分成两种，不使用“自动判断”隐藏用户选择：

- **直接洞察**：适合单一物料、明确型号或一个窄问题，直接生成该物料的行情、驱动、项目影响和行动建议。
- **分解型洞察**：适合模块、总成、系统或产业链，先生成并确认分解树，再对用户选中的叶子节点洞察，最后形成综合结论。

使用分段控件或两张简洁的模式卡表达差异，保持输入框和项目上下文不变。记住用户上一次选择即可，不增加复杂配置。

以下入口统一打开同一个工作区草稿，不复制业务逻辑：

- 分析成果 > 物料洞察顶部“新建物料洞察”。
- 右侧 AI 对话中识别到“洞察某物料”后的确认按钮。
- 项目 BOM 行的“洞察该物料”。
- 器件库行的“物料洞察”。
- 驾驶舱量产机会或关注物料卡片。

入口携带物料、项目、型号等上下文，但进入工作区后必须允许用户修改后再运行。

### 15.4 AI 只提示模式，不替用户决定

用户已明确选择一种模式后，程序只在范围明显不匹配时给出非阻塞提示：

- 直接洞察中输入“显示模块成本机会”时提示“范围较大，建议改用分解型洞察”，提供一键切换但不强制。
- 分解型洞察中输入明确单型号时提示“该对象可直接洞察，通常更快”，仍允许用户坚持分解。
- 从项目 BOM 批量选择多个明确物料时进入“直接洞察”的批量模式，不自动创建虚假的总成树。
- 模式切换保留输入、项目、物料和附件上下文，不立即触发模型调用。

提示优先使用本地关键词和对象数量规则，不为判断模式单独调用云端模型。

### 15.5 洞察首页

首页只保留“发起入口 + 顶层任务列表 + 少量建议”，避免三组卡片同时竞争注意力：

```text
┌─ 新建物料洞察 ────────────────────────────────────────────┐
│ 输入问题 / 关联项目 / 开始                                 │
└───────────────────────────────────────────────────────────┘

[全部] [待确认] [进行中] [已完成] [失败]
┌────────────────────────────────────────────────────────────┐
│ □ 显示模块成本机会     分解洞察 · 12节点 · 8已完成          │
│   关联 M280 · 预计影响 ¥18–26       [继续]                  │
├────────────────────────────────────────────────────────────┤
│ □ TST-PANEL-27QHD165   直接洞察 · 已完成                    │
│   趋势下降 · 中置信 · 更新于今天      [查看]                │
└────────────────────────────────────────────────────────────┘
```

总列表只显示父级任务。器件库“关注物料”不再整组复制到这里；最多在空状态或右上角折叠区显示 3–6 个“建议洞察”对象，点击后才创建任务。

任务列表支持搜索、状态筛选、关联项目筛选和排序。多选后支持批量继续、重试失败、归档、导出；子节点数量不计入父任务列表条数。

### 15.6 分解预览而非立即全部运行

复杂主题选择“先分解”后，第一步只生成可编辑树草稿，不立即对所有节点执行行情洞察：

1. 生成 2–3 层结构预览。
2. 用户可重命名、合并、删除、新增节点。
3. 系统根据成本占比、项目 BOM 影响和数据可得性预选 3–8 个高价值叶子节点。
4. 用户多选需要洞察的节点后点击“洞察所选”。
5. 未选节点保留为结构信息，不显示为失败或待处理噪音。

节点必须支持复选框、Shift 连选、选择同层、选择所有叶子、只选高影响、反选和清空。批量操作条显示选中节点数、预计调用次数及所用本地/云端模式。

禁止默认把几十个叶子节点全部提交模型。没有成本占比时，按用户选中范围执行，不伪造影响排名。

### 15.7 运行队列与长任务体验

洞察按节点增量执行并实时保存，每个节点独立成功或失败：

- 默认最多并发 2 个节点；同一云端供应商不支持并发时自动串行。
- 显示总体进度、当前节点、成功/失败/跳过数量和预计剩余调用数。
- 支持暂停、继续、取消未开始项和仅重试失败项。
- 关闭页面后任务状态保留，再次进入可继续。
- 单节点失败不能把整个父任务标记为失败；状态应为“部分完成”。
- 已完成节点立即可查看，不等待全部结束。
- 最终综合只在所选节点完成后运行一次；部分失败时明确基于多少节点，不伪装成完整结论。

云端需要确认时，只暂停需要云端的节点并说明原因；本地规则、数据库查询和已授权节点继续执行。

### 15.8 任务详情布局

任务详情采用高不透明度实体画布，保持现有蓝灰主题和清晰数据层级：

```text
┌─ 显示模块成本机会 ─ M280 ─ 部分完成 8/12 ────────────────┐
│ [整体结论] [分解结构] [历史变化] [证据]      [保存成果]    │
├──────────────────────┬─────────────────────────────────────┤
│ 分解树 / 节点清单     │ 当前结果                            │
│ □ 面板       已完成   │ 方向、幅度、置信度、时间            │
│ □ Scaler IC  运行中   │ 价格驱动与供应信息                  │
│ □ 电源板     待运行   │ 项目影响与建议动作                  │
│ □ 结构件     已跳过   │ 证据来源与数据缺口                  │
└──────────────────────┴─────────────────────────────────────┘
```

整体结论优先展示：一句话判断、趋势/价格区间、关键驱动、项目影响、建议动作、置信度和数据时间。禁止把模型原始 Markdown 长文直接作为主结果。分解结构使用可折叠树作为主要导航，React Flow 画布作为“查看结构图”切换视图，不强迫用户在大画布中完成所有日常操作。

节点结果必须包含：行情方向、区间或无法估算说明、成本占比、项目 BOM 影响、证据、更新时间和建议动作。没有数据时显示缺什么以及下一步，不用空图表补位。

直接洞察的默认结果布局：

```text
┌─ 一句话结论 ───────── 趋势 ↓ · 中置信 · 数据截至 09-02 ┐
│ 当前价格信号 │ 历史区间 │ 近几期变化 │ 关联项目金额      │
├──────────────────────────────┬──────────────────────────┤
│ 价格区间与趋势图             │ 主要驱动                 │
│                              │ ↑ 上行因素 / ↓ 下行因素  │
├──────────────────────────────┼──────────────────────────┤
│ 项目影响与历史基线           │ 机会、风险与建议动作     │
├──────────────────────────────┴──────────────────────────┤
│ 证据来源 · 数据缺口 · 分析口径                          │
└─────────────────────────────────────────────────────────┘
```

每张结论卡只表达一个意思；正文通常不超过 2–3 行，更多内容进入展开详情或证据抽屉。

### 15.8.1 分解树视觉与交互重构

分解型洞察必须把“结构理解”和“批量操作”分开处理：

- 默认使用紧凑可折叠树/树表完成选择、状态查看和批量操作。
- “结构图”切换为 React Flow 的视觉总览，适合查看层级与影响关系；日常多选不依赖在大画布中精确点小节点。
- 布局默认从左到右：根对象 → 模块/结构节点 → 终端物料。相同深度保持同一列，禁止节点重叠和连线穿过节点。
- 根节点使用主题主色实底；结构节点使用浅主色表面；叶子节点使用白色/深色实体卡并用左侧状态条表达状态。
- 节点只显示名称、成本占比或项目金额、洞察状态/趋势三个层级，不把长摘要塞入节点。
- 分支折叠后显示“包含 N 个节点、M 个已完成”；支持只看所选、只看高影响、只看失败和聚焦当前分支。
- 点击节点在右侧更新结构化详情；双击节点聚焦分支；面包屑可返回根对象。
- 连线保持低对比中性色；只有当前选中路径使用主题色，不用多色线制造噪音。
- 缩放后文字仍可读；小比例时隐藏次要标签而不是让文字互相覆盖。
- 成本占比未知时显示“待估算”，不以相同大小伪装成已知比例。

结构图只承担“看懂关系”的任务，成本贡献、趋势驱动和项目影响交给相邻图表表达。

### 15.9 图表与可视化

- 直接洞察：有连续快照时使用“中位/代表价格折线 + 高低区间带”；只有少数离散时点时改用点图或对比条，不绘制假趋势。
- 分解洞察：模块/节点成本贡献使用排序横向条形图；默认显示前 8，保留“查看全部”。
- 综合方向：只有节点影响能可靠相加时使用正负驱动瀑布图；否则使用按影响排序的上行/下行双向条形图。
- 项目影响：使用带历史基线和目标参考线的点图/区间图，并保留可精确查数的表格。
- 构成占比：优先使用 100% 堆叠条；只有 5 个以内互斥模块且粗略占比阅读更重要时才考虑环图。
- 图表点击定位树节点或明细行；Tooltip 显示口径、时间、来源和置信度。
- 所有时间图至少显示首个和最新日期；金额、百分比、数量在坐标轴、标签和 Tooltip 中保持同一单位。
- 单序列不制造彩虹色或多余图例；同一节点/模块在不同图表中保持稳定颜色。
- 图表标题描述画了什么，不写未经证据支持的营销式结论。
- 空数据、数据点不足和口径不一致时显示原因，不为了“更好看”补造数据。

页面的视觉签名是“可执行的洞察树”：结构节点、行情状态和项目影响在同一棵树中通过克制的状态色表达。除此之外保持安静，不增加无业务意义的装饰。

### 15.9.1 结构化结果契约

直接洞察、节点洞察和分解综合都必须先形成经过校验的结构化对象，再由 UI 渲染卡片与图表。禁止主界面直接消费模型返回的一整段 Markdown。

直接/节点洞察的最小结果结构：

```ts
type MaterialInsightResult = {
  headline: string;
  direction: '上涨' | '下降' | '震荡' | '信号不明确';
  confidence: '高' | '中' | '低';
  asOf: string;
  priceSignal?: {
    min?: number;
    max?: number;
    unit?: string;
    reference?: string;
  };
  drivers: Array<{
    title: string;
    direction: 'up' | 'down' | 'neutral';
    impact: 'high' | 'medium' | 'low' | 'unknown';
    explanation: string;
    evidenceIds: number[];
  }>;
  opportunities: Array<{ title: string; impactText: string; evidenceIds: number[] }>;
  risks: Array<{ title: string; severity: 'high' | 'medium' | 'low'; evidenceIds: number[] }>;
  actions: Array<{ action: string; reason: string; priority: 'high' | 'medium' | 'low' }>;
  projectImpacts: Array<{
    projectId?: number;
    projectCode: string;
    currentCost?: number;
    baselineCost?: number;
    potentialAmount?: number;
  }>;
  dataGaps: string[];
};
```

分解综合结果在上述结构外增加：

```ts
type DecompositionSynthesis = MaterialInsightResult & {
  coverage: { selected: number; succeeded: number; failed: number; skipped: number };
  nodeContributions: Array<{
    nodeId: number;
    name: string;
    costRatio?: number;
    direction: '上涨' | '下降' | '震荡' | '信号不明确';
    contribution?: number;
    evidenceIds: number[];
  }>;
};
```

实现要求：

- 使用现有解析与 Zod/手写校验能力；不为此新增依赖。
- 模型缺字段时用明确空值或 `dataGaps`，不能用猜测补齐。
- 所有金额、趋势点、成本占比和项目影响优先由本地数据库计算；模型负责解释和归纳，不负责凭文字制造图表数据。
- 图表从 `trend_snapshots`、分解节点、BOM、历史基线和已验证结构字段读取数据。
- `evidenceIds` 必须能打开对应证据；无证据的判断降低置信度并标注“待验证”。
- 原始模型文本可以保留在调试/证据区域，但不作为默认主视图。
- 结构化结果随分析成果保存，使重新打开时无需再次调用模型即可恢复相同卡片和图表。

如现有 `trend_snapshots` 无法保存完整结构，可幂等增加 `result_json TEXT DEFAULT '{}'`；不要再拆出一组一对一小表。

### 15.9.2 结构化结果的视觉顺序

结果页按决策顺序固定呈现，避免每次模型输出不同布局：

1. **结论**：一句话判断、方向、置信度、数据时间。
2. **关键数字**：价格区间、历史变化、关联项目金额、覆盖节点。
3. **证据图表**：趋势、贡献或项目影响中最有数据支撑的一至两张。
4. **为什么**：上行/下行驱动，按影响排序。
5. **怎么办**：机会、风险和下一步行动。
6. **依据与缺口**：来源、口径、时间和仍缺的数据。

同一结果默认不超过两张主图。更多图表放入“查看详细分析”，防止页面重新变成图表与卡片堆砌。

### 15.10 数据分层与兼容

首期不新增 `material_insight_tasks` 大表，优先复用现有数据：

- 顶层 `decomposition_tree` 根节点代表分解洞察任务。
- 未被非根分解节点引用的直接查询 `trend_item` 代表直接洞察任务。
- 被分解树子节点引用的 `trend_item` 只作为节点结果，禁止进入父任务总列表。
- 父任务整体结论使用根节点关联趋势、聚合快照或现有分析成果保存。

新增共享查询 `getMaterialInsightSubjects()`，在数据库查询层完成分组和去重，分析成果页和工作区必须共同使用，禁止两个页面各自实现不同过滤规则。

旧数据不删除、不重建。通过以下规则回填显示：

1. 有根节点的树按根节点合并为一条父任务。
2. 子节点关联的趋势项从总列表隐藏，但历史快照仍完整保留。
3. 其余快捷/直接趋势项各显示为一条直接洞察任务。
4. 无法判断归属的趋势项进入“待整理”，可批量并入某父任务或保留独立。

只有现有表无法可靠表达“跨页面恢复的运行队列”时，才增加一个最小任务运行表，字段限于父对象、队列 JSON、状态、进度和更新时间；不要重建趋势与分解数据。

### 15.11 交互与动效

- 树展开、节点状态变化使用 160–200ms `transform/opacity` 过渡。
- 结果区切换使用 180–220ms 淡入，不让图表和文字大幅位移。
- 运行进度使用稳定进度条；完成时状态点短促过渡一次，不使用循环闪烁。
- 高频多选、筛选和树导航即时响应，不添加装饰动画。
- 列表滚动时不做逐卡入场动画。
- 必须遵循现有动效开关与 `prefers-reduced-motion`。

### 15.12 实施位置

优先修改和复用：

- `src/pages/Decomposition.tsx`：收敛为物料洞察工作区。

### 15.13 补充验收场景

1. 在分析成果页选择“直接洞察”，输入“27英寸QHD面板近期是否有降价空间”，产生一条直接洞察父任务。
2. 选择“分解型洞察”并输入“显示模块成本机会”，先显示优化后的分解树预览；选择 5 个叶子运行后，总列表仍只有一条父任务。
3. 旧分解树包含 20 个关联趋势项时，物料洞察列表只显示一个根任务，20 个节点可在详情树查看。
4. 批量洞察 10 个节点，其中 2 个失败，父任务显示“部分完成 8/10”，可仅重试失败项。
5. 关闭并重新打开应用后可继续未完成队列，已完成节点结果不丢失。
6. 从项目 BOM 行发起洞察时自动带入项目和物料上下文，但运行前可修改。
7. 直接洞察和分解洞察均可保存为一条父级分析成果，子节点不重复进入成果库。
8. 快捷物料、关注物料和历史趋势旧数据均可查看，不出现重复父项。
9. 100 个父任务、单任务 100 个节点时，搜索、多选和切换保持可用。
10. 动效关闭、减少动态效果及全屏情况下，Modal、Select、树和图表均正常显示。
11. 洞察完成后主结果由固定结构卡片和最多两张主图组成，不直接展示整段模型 Markdown。
12. 缺少连续价格点时不显示折线趋势；缺少可加总贡献时不显示瀑布图，并给出明确数据不足说明。
13. 分解结构图在 100 个节点下无节点重叠，支持折叠、聚焦分支、状态筛选和从图表定位节点。
14. 保存并重新打开成果后，结构化卡片、图表、证据引用和当时的数据版本保持一致，无需重新调用模型。
