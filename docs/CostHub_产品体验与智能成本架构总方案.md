# CostHub 产品体验与智能成本架构总方案

> 文档状态：实施主文档  
> 版本：1.0  
> 日期：2026-09-03  
> 适用范围：当前单人、本地、免安装版本；兼顾未来团队化，但不提前实现多人系统  
> 目标读者：产品所有者、实现工程师、后续交给 Luna 的开发任务  

---

## 0. 文档定位

本文档是 CostHub 后续产品和技术演进的唯一主方案。现有的 ODM 工作台方案、Pi Agent Runtime 方案、AI 提升规划等文档继续作为背景材料和实现证据，不再分别定义新的页面、数据实体或第二套流程。

后续实现遇到冲突时，按以下优先级决策：

1. 本文档已经确认的业务规则。
2. 当前数据库中已经存在且验证可用的数据资产。
3. 当前 AI 工具契约、安全策略和审计机制。
4. 旧文档中的局部设计。

总原则是：不推倒重来，不重复建设，不为了未来团队化提前增加复杂度。

---

## 1. 核心结论

CostHub 不应继续发展成“若干数据页面 + 一个聊天框”，而应成为一个以项目成本决策为主线的本地成本工作台：

- 项目是业务主轴：从 Charter 估算、价值取舍、领域目标、供应商报价、招标定点、Open BOM、阶段冻结到量产后降本，全部落在同一项目时间线上。
- 数据是事实底座：任何成本数字都必须能回到 BOM 版本、报价批次、价格记录或人工输入。
- AI 是贯穿式能力：AI 不再拥有一套独立业务页面；侧边栏、全屏工作台和项目内入口共享同一会话、同一任务、同一结果。
- 规则负责计算，模型负责理解和解释：金额汇总、差异拆分、目标分解、重复判断均由确定性代码完成，本地模型负责归类建议、假设说明、自然语言总结和复杂关系辅助识别。
- 云端只是受控的公开情报工具：云端永远不能直接访问数据库，也不能成为拥有本地上下文的第二个 Agent。
- 所有关键结论可核验：最终结果必须同时提供结论、计算过程、引用数据、数据版本、置信度、缺失信息、工具轨迹和实际外发内容。
- 自动巡视以“不打扰”为合格标准：相同事实只提示一次；只有证据、影响或状态变化时才重新提醒。

### 1.1 本期不做

- 不做团队账号、角色权限、审批流和云同步。
- 不做采购、库存、良率、质量、物流、税务、账期、MOQ 和汇率系统。
- 不把整套 Hermes、DeepSeek Harness 或通用编码 Agent 引入应用。
- 不允许 AI 执行任意 SQL、Shell、文件或网络操作。
- 不开发第二套报告、对比、AI 会话或提醒模块。
- 不追求完全自动完成成本工作；关键映射、基线、价值分类、目标冻结和定点结论均由人工确认。

## 2. 已确认的业务边界

### 2.1 使用者与部署

- 当前用户：单人成本经理。
- 当前产品形态：Windows 桌面端，Tauri + React + SQLite。
- 部署偏好：免安装、可复制运行。
- 数据规模：
  - 同时管理约 10–20 个项目。
  - 每个项目约 100–200 行 BOM。
  - 每年新增约 5–10 个项目。
  - 每个品类约 3–10 个历史项目。
  - 每个项目通常 2–3 家 ODM、2–3 轮报价。
  - 用户原声条数随可获取评论量变化。

该规模不需要服务端数据库、消息队列、向量数据库或微服务。SQLite 和进程内任务队列足够。

### 2.2 产品范围

CostHub 需要支持显示器、手写笔、鼠标、包、Dock 等不同品类。不同品类共用项目、成本、供应商、阶段和分析方法，但规格字段不同，因此规格模型必须由品类模板驱动，不能继续在 projects 表中不断增加显示器专属列。

### 2.3 成本口径

本系统管理标准成本，统一拆成四层：

1. 物料 BOM。
2. 包装成本。
3. ODM 加工费。
4. 平台费。

标准成本 = 物料 BOM + 包装成本 + ODM 加工费 + 平台费

其中包装可以作为一个领域参与目标分解；ODM 加工费作为“制造/ODM”领域单列；平台费按现有业务规则以金额或费率计算并单列，不分摊给研发领域。

为避免新增一套成本明细表，物料、包装和 ODM 加工费继续使用 BOM 行承载，并增加 cost_layer 标识；平台费由项目配置计算。所有页面默认展示标准成本总计，也允许展开查看四层构成。

暂不纳入：

- 利润。
- 采购、库存、良率和制造损耗。
- 税务、汇率、物流、MOQ、账期。

现有 profit_rate 作为历史兼容字段保留，但不得混入标准成本、目标达成和成本基线。现有 platform_fee_rate 继续复用，页面必须同时显示费率、计费基数和计算后金额。

### 2.4 项目阶段

统一阶段为：

1. Charter。
2. CDCP。
3. PDCP。
4. ADCP。
5. 量产后降本。

关键事实：招标在 CDCP 前完成，Charter 到 CDCP 前成本基本定型。因此产品的主流程不能把招标当成 CDCP 之后的动作。

### 2.5 Charter 的最小输入

- 产品定位或目标售价。
- 关键规格。
- 上一代或主要参考项目。
- 预计销量。
- 研发初步方案。
- 财务给定的整机目标成本。

财务目标成本由用户录入，CostHub 不反推、不替财务决定。

### 2.6 敏感数据

以下信息绝不允许离开本机：

- 项目代号和可识别项目的信息。
- 供应商名称及其映射关系。
- 项目中的器件型号和规格。
- 单价、总成本、目标成本和报价。
- 原始 BOM、报价文件和差异明细。
- 用户原声原文及其来源文件。

允许发送云端的信息：

- 通用物料名称。
- 已确认属于公开目录的器件型号。
- 不带项目、供应商和价格上下文的行业问题。
- 去项目化表达的公开产品规格，例如“27 英寸、4K、160Hz、MiniLED”。

## 3. 当前系统审计与改造判断

### 3.1 应直接复用的能力

当前代码已经具备以下底座，不应重写：

| 已有能力 | 当前资产 | 后续定位 |
|---|---|---|
| 项目、BOM、器件、模块、竞品 | SQLite 表和 db 模块 | 核心事实数据 |
| 项目阶段评审、目标、措施 | project_cost_reviews、project_targets、project_measures | 扩展版本和状态，不另建平行模块 |
| 报价轮次与规格基线 | project_spec_baselines、tender_rounds、supplier_quote_batches、supplier_quote_lines | 供应商工作台主数据 |
| 报价行匹配与谈价项 | quote_line_matches、negotiation_items、tender_decisions | 保留并增强 |
| 用户原声 | voice_item、voice_dimension、voice_run | 增加来源、去重和人工确认 |
| 卖点与模块映射 | selling_points、selling_point_modules、selling_point_dims | 改造成价值取舍工作区 |
| 成果与工作手账 | analysis_artifacts、work_logs | 统一结果引用，不复制数据 |
| AI 运行与证据 | ai_analysis_runs、ai_recommendations、EvidenceRef、VerifyResult | 成为统一结论契约 |
| Pi Runtime | 已接入的 Pi Core、事件流、工具调用和中止能力 | 继续作为单 Agent 运行时 |
| 安全与审计 | tool manifest、approval grants、egress audit、write audit | 分离本地审计和云端外发审计 |
| 物料行情 | trend 系列表及映射 | 量产后降本信号来源 |

### 3.2 需要纠正的结构性问题

1. App 同时存在“AI 工作台”和永久右侧 AI 面板，形成两个入口和两套空间占用。
2. Projects.tsx、AiPanel.tsx、Settings.tsx 过大，页面承担数据、业务计算、弹窗和 AI 编排多种职责，影响修复速度。
3. 项目详情以 8 个平级 Tab 呈现，用户需要自己拼接阶段过程。
4. Dashboard、分析成果、项目分析、AI 情报和报告存在语义重叠。
5. 当前领域目标分解使用用户声量影响成本份额，方法不适合作为正式目标分解。
6. 原声频次被过度等同于价值；基础特性可能很少被正向提及，但不能删除。
7. 巡视主要由定时器驱动，缺少稳定的问题身份、证据版本和重开规则。
8. 本地模型调用日志、云端请求日志、审批记录混在设置体验中，用户难判断是否真实外发。
9. 图表散落在页面内自行拼装，AI 可视化和业务页面可视化不能共享定义。
10. 当前打包主包偏大，且部分同一模块同时静态和动态导入，懒加载没有真正生效。

### 3.3 不应继续扩大的旧逻辑

src/targetAllocation.ts 中“按历史成本份额与用户声量混合分配目标”的逻辑，只能保留为探索性价值视图，不能作为正式领域目标。

sellingPointAnalyzer 中把模块成本按声量分摊到卖点的结果，只能表示“估算归因”，不得冒充可核算成本。一个模块支持多个特性时，用户必须确认归因比例或允许显示为共享成本。

### 3.4 现有功能逐模块优化清单

本节处理“已经有的功能怎么变得更合理”。结论不是全部重做，而是明确保留、改造、合并和停止扩展。

| 现有模块 | 保留的价值 | 使用逻辑调整 | 唯一主归属 |
|---|---|---|---|
| AI 工作台 / Dashboard | 风险、机会、待确认、项目进展 | 改为今日工作台；没有待办时保持安静，不用“启动一次巡检”填空 | 今日工作台 |
| 项目管理 | 项目主档、BOM、目标、阶段、措施、ODM、SKU | 从 8 个平级 Tab 改为 5 个阶段工作区；所有项目成本动作在这里闭环 | 项目 |
| BOM 清单 | 模块分组、全量表格、引用、内联编辑、自定义列、软删除 | 增加版本和导入预览；项目价格不得反向覆盖器件主档价格 | 项目 → BOM 版本 |
| 器件库 | 标准名称、型号、规格、分类、历史报价 | 从“单一当前成本表”改为“器件主档 + 多来源价格证据”；项目归属由关系表派生 | 资料库 → 器件 |

| 供应商管理 | ODM 主档、历史报价、关联项目 | 聚焦 2–3 家 ODM 的成本证据；质量、份额、地图和综合评分无真实数据时不作为核心 | 资料库 → ODM |
| 竞品管理 | 独立竞品资料、竞品 BOM、估价 | 保持与自有项目隔离；导入一次后在项目内引用，不在多个页面重复维护 | 资料库 → 竞品 |

| 成本报告 | 单项目和项目对比输出 | 合并为项目“生成阶段成本包”，复用同一数据和图表 | 项目右上角 |
| 用户原声 | Excel 导入、本地分块分析、维度汇总 | 移入项目价值取舍；补来源、去重、抽样和人工 Kano 分类 | 项目 → 价值取舍 |
| AI 审价助手 | 报价异常解释 | 合并到报价导入和谈价清单，不保留第二个审价页面 | 项目 → 报价与定点 |
| 物料洞察 | 公开行情、分解树、来源、历史快照 | 默认变成关注清单；仅复杂物料按需展开分解树，避免每次都走大流程 | 情报 → 物料行情 |

| AI 情报弹窗 | 报价差异、自主建议、巡检发现 | 合并成今日工作台“待处理”，项目页只显示该项目过滤结果 | 今日工作台 |
| 设置 | 模型、供应商、主题、日志、安全 | 收敛为连接、安全、数据、外观、诊断五组；日志按本地/外发/写入分离 | 设置 |
| 全局搜索 | 器件、项目、竞品跳转 | 保留并补充报价批次、成果和措施；结果直接到具体对象 | 全局能力 |

### 3.5 现有数据使用逻辑必须先纠正

#### 3.5.1 器件成本不是一个可被最后一次导入覆盖的值

当前 parts.cost 容易被理解为“该器件的真实成本”，但 ODM 场景下同一器件会因供应商、项目、时间和轮次不同而有多个报价。

调整后：

- parts 只保存器件身份、标准名称、公开型号、规格和分类。
- 价格事实保存在项目 BOM 行、供应商报价行和价格历史。
- parts.cost 暂时保留为兼容显示值，标记为“最近参考价”，禁止作为正式基线直接参与结论。
- 导入项目 BOM 时不得因为型号匹配就改写其他项目看到的器件价格。
- 器件详情显示最低、最新、中位数、来源数和时间，不只显示一个成本。
- 正式基线来自 cost_baseline_decisions 的人工确认。

这是最高优先级的数据可信修正。

#### 3.5.2 模块库不再维护第二份器件清单

当前 modules/module_items 与 project_boms 都可以表达“项目里的模块和器件”，长期会出现一边更新、另一边没更新。

调整后：

- project_boms 是项目 BOM 事实。
- 模块库按项目 BOM 动态聚合模块成本、器件组成和跨项目差异。
- module_items 仅兼容旧数据；迁移确认后停止新增和编辑。
- 模块名称规范和别名继续由 module_rules/人工确认维护。
- 如果未来确实需要方案模板，再从已冻结 BOM 版本显式创建模板；本期不提前建设。

#### 3.5.3 项目关联使用 ID，不使用名称字符串

当前器件 projects 字符串、用户原声 product 字符串和工作手账 work_project 名称，容易因项目改名、重名和代号调整造成断链。

调整后：

- 业务关系统一保存 project_id。
- 页面仍显示代号和名称。
- 旧字符串通过项目代号优先、名称次之做一次迁移；无法唯一匹配的记录进入人工确认。
- 原始字符串保留在 source_label，方便追溯。

#### 3.5.4 当前成本、冻结成本和历史快照必须分开

- 当前成本：可编辑 project_boms 汇总。
- 冻结成本：project_bom_versions 汇总。
- 阶段成本：某阶段引用的冻结版本。
- 报价成本：某 supplier_quote_batch 汇总。
- 快照：当时计算结果和引用版本，不是另一份可编辑 BOM。

页面上每个“成本”旁必须显示类型和时间，禁止笼统显示“项目成本”。

#### 3.5.5 软删除必须有恢复入口

现有 project_boms.is_deleted 保留。BOM 页增加“回收站”，显示删除人、时间和来源；恢复时不得破坏冻结版本。永久删除只用于从未被任何冻结版本或结论引用的数据。

### 3.6 各现有页面的具体体验调整

#### 今日工作台

保留：

- 招标项目进度。
- 今日优先处理。
- 目标风险和报价机会。
- 最近分析。

调整：

- “项目成本分布”只有在用于识别异常时才保留；纯排序图不占首屏。
- 没有任务时显示“当前无待处理事项”，不主动制造巡检任务。
- 报价情报、巡检发现和自主建议不再通过项目页弹窗集中处理。
- 后台扫描进度放入 AI 任务中心，不使用全局顶栏长期占位。
- 云端待审批只在确实阻断某项公开研究时出现，且不挡住本地工作。

#### 项目管理

保留：

- 左侧项目快速切换。
- 项目分组和排序。
- 领域目标卡。
- BOM 模块分组/全量表格。
- 引用项目、差异、成本历史、阶段评审、措施、ODM 和 SKU。

调整：

- 进入项目时仍能看到全局五个导航，项目列表作为第二级导航，不让用户被困在项目模式。
- 项目页头直接显示阶段、标准成本口径、冻结状态和数据新鲜度。
- 原有“成本分析”不再重复一套静态图，按“上一代桥、目标、报价、价值”四类任务展示。
- 原有“整机成本历史”改为事件时间线，明确每个点引用哪个 BOM 版本。
- “成本测算”统一改名“阶段评审”，阶段只能使用已确认枚举。
- “ODM”并入报价与定点，不再单独维护整机报价和另一份轮次历史。
- 自定义 BOM 列保留，但不可用它代替正式字段；系统识别到“目标价、供应商价、状态”等常用列时引导迁移到正式功能。

#### 器件库

保留：

- 搜索、分类、批量选择、Excel 导入导出。
- 器件别名、供应商来源、价格历史和变更轨迹。

调整：

- 默认表格列改为：标准名称、型号、核心规格、分类、有效报价区间、最新价、基线价、来源数、更新时间。
- “成本”编辑改为“录入价格证据”，必须选择来源类型和时间。
- 项目筛选按 project_id 关系查询，不读取 parts.projects 文本。
- 同规格器件合并必须先预览引用影响。
- 明确区分“同型号”“同规格等效”“相似参考”，不能全部当成同一器件。

#### 模块库

保留：

- 跨项目模块成本对比。
- 模块器件组成。
- 品类和项目筛选。
- 横向条形图和明细表。

调整：

## 6. 统一领域模型

### 6.1 主实体关系

项目是聚合根，其他信息围绕项目引用：

项目  
├─ 品类规格模板 → 当前规格值 → 规格基线版本  
├─ 参考项目 → 参考冻结 BOM  
├─ 变更包 → 删除行、替换行、新增行、依赖行  
├─ 成本目标版本 → 领域目标 → 机会依据

├─ 用户原声来源 → 维度 → 特性分类 → 模块映射  
├─ 竞品 → 规格/成本比较  
├─ 措施、谈价项和阶段快照  
└─ AI 运行、建议、证据、成果和工作记录

### 6.5 成本基线

CostHub 需要三类基线，但不需要三套互不关联的价格库：

1. 项目参考基线：上一代冻结 BOM 或最相似项目。
2. 物料价格基线：同规格可比物料的已确认最低有效价格。
3. 模块基线：可比项目中该模块的合理区间和低位参考。

- id
- baseline_type：project、part、module
- category
- scope_key
- source_type
- source_ref_id
- value
- comparable_rule_json

- confirmed_at

基线价格仍来源于 BOM 版本、报价批次和价格历史，决策表只记录“用户为何认可它为基线”，不复制价格历史。

物料基线规则：

- 只有规格完全一致或人工确认等效的记录才进入候选集。
- 默认显示最低价、中位数、样本数、来源项目数和时间。
- “最低”不是自动生效；用户确认后才成为正式基线。
- 规格、时间有效性或证据变化后生成新候选，不覆盖旧基线。
- 样本不足时显示“参考价”，不得显示“正式基线”。

### 6.6 成本目标版本

现有 project_targets 保存当前领域目标。增加 project_target_versions 作为冻结头，领域明细可继续复用 project_targets 并补充 version_id、baseline_cost、opportunity_amount、allocated_challenge、override_reason、status。

每次重新分解创建新版本，旧版本只读。禁止静默覆盖。

### 6.7 数据版本与指纹

任何 AI 分析和报告必须保存：

- data_fingerprint：输入事实的稳定摘要。
- source_version_ids：BOM、规格、报价、目标的版本 ID。
- generated_at。
- stale 状态：源版本发生变化后自动标记。

“结论仍能打开”与“结论仍然有效”是两个不同状态。

## 7. Charter 成本估算

### 7.1 目标

在资料不完整的 Charter 阶段，用历史项目和研发初步方案形成一个可解释、可更新的成本区间，不伪装成精确报价。

### 7.2 工作流

1. 选择一个主要参考项目，可补充两个次要参考。
2. 系统读取参考项目的冻结 BOM 和规格。
3. 对照新品规格，生成待确认差异。
4. AI 基于历史 BOM 和模块关系建议变更包。
5. 用户确认、拆分、合并或拖拽变更包内的器件。
6. 对新增或无法匹配物料选择历史相似器件或输入研发 should-cost。
7. 规则引擎汇总确定项、估算项和缺失项。
8. 输出低位、当前判断、高位三个成本值和成本桥。
9. 用户冻结 Charter 估算版本。

### 7.3 估算公式

调整后可分解基线 = 参考冻结 BOM 中的物料、包装和 ODM 加工费  
+ 已确认新增成本  
− 已确认删除成本  
+ 替换后成本 − 替换前成本  
+ 数量变化影响

调整后标准成本 = 调整后可分解基线 + 平台费

估算区间只对不确定项展开：

- 已知历史价格：使用有效可比记录的区间。
- 研发 should-cost：记录为人工来源。
- 无数据项：不填 0，标记缺口并单列预留。

### 7.4 页面

左侧为“参考 BOM”，中间为“变更包画布”，右侧为“成本桥和缺口”。

拖拽只用于归组和确认，不让拖拽动作直接修改金额。金额变化仍由规则重新计算。

## 8. 用户价值与功能取舍

### 8.1 方法

采用轻量版 Kano + QFD + 价值工程，不构建完整质量屋，也不要求大量问卷数据。

每个特性只需完成四步：

1. 原声主题：AI 从评论中归纳并附原文证据。
2. 人工分类：基础、性能、惊喜、无感、反向。
3. 规格与模块关联：AI 建议，用户拖拽确认。
4. 价值结论：必须满足、值得投入、需要降本、不做。

### 8.2 原声使用规则

- 评论频次代表“被提及程度”，不直接代表愿付价格。
- 负面评论天然更容易出现，不能简单与正面次数相减后当价值。
- 基础特性即使提及少，也必须满足。
- 新品无历史原声时，可引用上一代或同品类公开评论，但必须标记来源产品。
- 每个主题显示样本数、来源平台、采集时间、去重后数量、正负样例和人工确认状态。
- 原文仅本地保存。

### 8.3 最简价值卡

每张特性卡包含：

- 特性名称。
- Kano 类别。
- 用户证据。
- 我方规格与竞品规格。
- 支撑模块。
- 估算成本。
- 对目标成本的影响。
- 决策：必须满足、保留投入、寻求等效降本、不做。
- 决策理由和确认人。

不再设置复杂的三级可信度。界面只显示“已确认 / 待确认”；AI 结论仍保留高、中、低置信度。

### 8.4 成本长城图

每次只选择一个竞品，避免多竞品叠加无法阅读。

图表定义：

- X 轴：可比较的特性或规格维度。
- 柱状图：规格差异分。定义为“竞品 − 我方”，正值表示竞品更好，负值表示我方更好。
- 成本曲线：对应特性归因成本差。定义为“竞品成本 − 我方成本”，正值表示竞品在该特性上成本更高，负值表示我方成本更高。
- 两个 Y 轴必须共用同一条零线，正负区清晰分色。
- 柱和成本点都显示直接标签，不能要求用户只看 Tooltip。
- 低置信度成本映射使用虚线和空心点。

四个象限的解释：

| 规格差异 | 成本差异 | 含义 |
|---|---|---|
| 竞品更好 | 竞品更贵 | 合理投入，判断用户是否愿意买单 |
| 竞品更好 | 竞品更便宜 | 我方高风险，优先改善 |
| 我方更好 | 我方更贵 | 检查是否过度设计 |
| 我方更好 | 我方更便宜 | 我方优势，适合固化 |

规格分不能跨维度直接比较绝对值。每个规格字段由模板定义比较方向和归一化规则；无法客观归一的字段由用户手工给出 −2 至 +2。

点击任一特性后展开：规格原值、评分规则、双方 BOM 映射、成本计算、用户证据和人工确认记录。

## 9. 领域目标成本分解

### 9.1 原则

领域目标不是把整机目标按历史成本占比切开，也不是按用户声量分配。正式分解必须回答：

- 当前合理基线是多少。
- 哪些钱因为规格或架构变化必须增加。
- 每个领域有多少可兑现机会。
- 整机挑战缺口是否可行。

用户价值只作为保护和取舍边界，不作为金额分配权重。

### 9.2 分解步骤

1. 用户录入财务整机标准成本目标。
2. 选择并确认参考项目。
3. 由变更包计算各领域“调整后基线”。
4. 根据平台费规则得到可分解目标。
5. 对每个领域录入或确认机会池。
6. 按机会池分配挑战缺口。
7. 检查总目标是否可行。
8. 用户手工调整并填写原因。
9. 冻结目标版本。

### 9.3 机会池

每个领域机会由以下来源组成：

- 设计机会：器件替换、方案简化、规格收敛。
- 历史基线机会：当前成本高于同规格已确认基线。
- 竞品机会：竞品同功能实现成本更低。
- 供应商竞争机会：其他 ODM 或其他项目已有更低报价。
- 行情机会：公开行情下行但报价未体现。
- 标准化机会：跨项目复用或减少定制。

每条机会包含金额区间、证据、责任人、技术风险和人工确认状态。正式分解只使用已确认金额。

### 9.4 计算方法

可分解基线 = 物料 BOM + 包装 + ODM 加工费

如果平台费是固定金额：

可分解目标 = 财务标准成本目标 − 固定平台费

如果平台费率 p 以可分解成本为基数：

可分解目标 = 财务标准成本目标 ÷ (1 + p)

挑战缺口 = max(0, 调整后可分解基线 − 可分解目标)

领域确认机会 = 该领域已确认机会金额之和

初次分配挑战 = 挑战缺口 × 领域确认机会 ÷ 全部领域确认机会

领域目标 = 领域调整后基线 − 分配挑战

如果某领域初次分配超过其确认机会，则以确认机会为上限，剩余缺口在其他仍有余量的领域继续分配。

如果挑战缺口大于全部确认机会，系统必须显示“目标不可行，仍缺 X 元依据”，不能为了数字相等强行压到最大领域。领域目标求和、平台费和标准成本目标必须在页面底部重新勾稽。

### 9.5 目标达成

领域达成率建议统一为：

达成率 = 1 − max(0, 当前成本 − 目标成本) ÷ max(基线成本 − 目标成本, 最小精度)

- 基线时为 0%。
- 达到目标时为 100%。
- 优于目标时显示“已超额达成”，不显示大于 100% 的误导百分比。
- 没有基线或目标时显示“不可计算”。

界面同时显示当前成本、目标、基线、已确认机会、已落实降本和剩余缺口，不能只显示一个百分比。

## 10. 报价、谈价与招标

### 10.1 主流程

1. 基于当前规格基线创建报价轮次。
2. 导入 2–3 家供应商的标准化 Excel。
3. 先预览列映射、总额校验、重复文件和异常行。
4. 导入后冻结原始报价批次。
5. 规则完成同物料匹配、模块汇总和轮次差异。
6. AI 仅处理疑似替换、规格描述和归类建议。
7. 用户确认匹配关系。
8. 系统生成供应商差异、议价清单和挑战目标。
9. 新一轮报价重复以上步骤，并区分价格变化与规格变化。
10. CDCP 前记录中标 ODM 和最终定点成本。

### 10.2 报价导入

继续采用“用户先整理成固定 Excel 格式”的现实路径，不投入通用 Excel 猜表系统。

导入预览必须显示：

- 项目、供应商、轮次、规格基线。
- 识别列和必填列。
- 总行数、有效行、异常行、重复行。
- 文件 Hash 和是否已导入。
- 原始总额与系统汇总差异。
- 即将新增的数据版本。

只有用户点击确认后才写库。

### 10.3 报价差异拆分

两轮总成本差必须拆成：

- 纯价格变化。
- 数量变化。
- 新增物料。
- 删除物料。
- 替换物料。
- 规格基线变化。
- 无法解释的残差。

规则计算必须保证各项之和等于总差异；不相等时禁止生成正式结论。

### 10.4 谈价辅助

对每个供应商生成独立清单：

- 当前报价。
- 本供应商上一轮报价。
- 其他供应商最低可比报价。
- 历史已确认基线。
- 推荐挑战价。
- 可讨论的设计路径。
- 证据来源和可外说/仅内部标签。
- 谈价状态和结果。

理论最低价只作为谈判锚点，不自动作为中标价，也不将其他供应商身份暴露给目标供应商。

### 10.5 定点

本期只记录最终成本和人工说明，不扩展质量、交付或综合打分模型。

定点后生成：

- 中标供应商。
- 最终定点成本。
- 与上一代、Charter 估算、财务目标的差异。
- 各领域达成。
- 未兑现机会和后续措施。

## 11. Open BOM、试制变更与最终 BOM

### 11.1 导入与冻结

中标 ODM 的 Open BOM 导入时创建 award_openbom 版本。导入流程与报价一致：预览、映射、校验、确认、冻结。

### 11.2 试制变更

任何结构性变化先创建变更包，再作用到当前 BOM：

- 用户选择受影响的旧行和新行。
- AI 可建议依赖关系。
- 用户确认后生成影响金额。
- 变更包写入项目时间线。

零散数量或价格修改仍可直接编辑，但冻结下一 BOM 版本时必须自动生成差异记录。

### 11.3 最终 BOM

量产前谈价完成后冻结 final_bom：

- 必须能够与 award_openbom、CDCP 和上一版本逐项比较。
- 必须列出仍未关闭的临时料、估价料和缺失规格。
- final_bom 成为量产后降本的正式基线。

## 12. 量产后降本

### 12.1 机会来源

- 物料公开行情变化。
- 采购或供应商反馈。
- 新项目出现同规格更低价。
- 距上次谈价超过设定时间。
- 已批准替代方案。

### 12.2 闭环

信号 → 候选机会 → 人工确认 → 谈价/设计措施 → 供应商反馈 → 已实现/未实现 → 更新价格版本 → 复盘

状态统一为：

- 候选
- 已确认
- 执行中
- 已实现
- 未实现
- 放弃

“预测节省”和“已实现节省”必须分开统计。已实现节省必须引用新价格或新 BOM 版本。

## 13. 自动巡视

### 13.1 优先巡视的五类问题

按优先级：

1. 新项目报价高于历史已确认基线。
2. 同规格物料跨项目价格不一致。
3. 行情下行但量产价格未调整。
4. 领域措施长期未关闭。
5. 目标成本超标。

### 13.2 调度方式

采用“事件触发优先、空闲轮询补充”：

- BOM、报价、目标、行情或措施变化后，立即只扫描受影响范围。
- 用户没有前台 AI 任务时，后台按类别轮换补扫。
- 用户发起任务时，后台任务让路并保存扫描游标。
- 不每 60 秒重新扫描全库。
- 同一轮只运行一个重任务，符合本地 24GB GPU 的实际限制。

### 13.3 去重身份

每个问题计算：

- issue_key：问题类型 + 业务对象稳定 ID + 规则版本。
- evidence_fingerprint：本次证据和关键数值的摘要。
- impact_band：影响金额档位。

处理规则：

- issue_key 相同且 evidence_fingerprint 相同：只增加发现次数，不通知。
- 证据未变但影响金额小幅波动：更新卡片，不通知。
- 证据变化、影响档位变化或状态恶化：重新通知。
- 用户忽略后，只有 evidence_fingerprint 变化才重开。
- 用户关闭后，条件消失则自动完成；再次出现新证据时可生成新事件。

### 13.4 复用现有表

不新建第二套巡检表。在 ai_advisor_insights 增加：

- issue_key
- evidence_fingerprint
- first_seen_at
- last_seen_at
- last_notified_at
- occurrence_count
- dismissed_fingerprint
- severity
- impact_amount

保留现有 fingerprint 作为迁移兼容字段。

### 13.5 提醒体验

- 无新事实时完全安静。
- 首页只显示“新增 N 条”，不显示后台每次扫描成功。
- 单日普通提醒设上限；高影响问题不受上限限制。
- 卡片必须提供“查看证据、转为措施、忽略、以后提醒”。
- 已忽略问题默认不占未读数。

## 14. AI 成本助手架构

### 14.1 架构选择

本期使用一个本地协调 Agent，不采用多 Agent。

原因：

- 当前数据量和任务并不需要多 Agent。
- 单张 RTX 4500 24GB 同时运行多个 27B 推理任务会增加等待和上下文竞争。
- 数据安全、工具审计和结果核验在单 Agent 下更容易封闭。

继续复用已经接入的 Pi Core：

- 事件流。
- 工具执行。
- 中止。
- steering 和 follow-up。
- 工具前置钩子。

从 Hermes 借鉴“只有用户确认的事实进入长期记忆”和“可复用成本技能”，不引入它的终端、消息、调度和子 Agent 表面。

从 DeepSeek Harness 借鉴轨迹记录、回放和评测思想，不把开发预览版运行时或通用执行器嵌入 CostHub。

### 14.2 单 Agent 工作环

用户请求  
→ 确定性意图路由  
→ 选择最小工具集合  
→ 本地数据工具查询  
→ 规则计算  
→ 如缺公开实时信息，构造受控外发请求  
→ 安全策略判断/必要时审批  
→ 云端只返回公开资料  
→ 本地模型综合  
→ 验证器检查数字和证据  
→ 生成结构化结论与可视化  
→ 用户确认后才写回业务数据

云端返回内容视为不可信资料，只能作为引用来源，不能直接写数据库或执行工具。

### 14.3 工具设计

保留现有 Tool Manifest，并遵循：

- 读工具默认无确认。
- 计算工具默认无确认。
- 写工具先展示变更摘要，用户确认后执行，并保留撤销记录。
- 云端工具只走唯一外发网关。
- 每次任务只给模型 6–10 个最相关工具。
- 工具返回统一 AiToolResult，必须有 summary、data、evidence、warnings、freshness。
- AI 不直接拼 SQL。

不再新增“万能查询工具”。缺能力时增加窄而可测的业务工具。

### 14.4 速度策略

目标不是让 27B 模型每件事都快，而是让用户立即知道任务在推进：

- 规则查询、汇总和已定义图表无需调用模型。
- 简单问答使用同一模型的 think=false 快路径。
- 深度估算、变更包建议、原声归纳使用思考模式。
- 先在 200ms 内显示任务已接收和计划步骤。
- 工具开始、完成、等待审批均实时显示。
- 数据指纹相同的分析结果可复用，并明确标记“复用上次结果”。
- 上下文只保留最近会话摘要和当前项目所需证据，不发送整库。
- 工具大结果先本地聚合，再给模型摘要。
- 用户任务永远高于后台巡视。

后续只有在测量证明路由耗时明显时，才考虑增加小模型；本期不新增模型依赖。

### 14.5 结果契约

最终结论固定包含：

1. 结论。
2. 计算过程。
3. 引用数据，可点击回到项目/BOM/报价。
4. 数据版本与生成时间。
5. 置信度。
6. 缺失信息和假设。
7. 工具轨迹。
8. 实际外发内容。
9. 建议下一步。

模型的原始隐式思维过程不保存、不展示。界面展示的是“工作进度摘要 + 工具轨迹 + 计算依据”。生成最终结论后，进度和工具卡自动收起，用户可展开核查。

### 14.6 记忆

只允许以下信息进入长期记忆：

- 用户明确确认的器件别名和等效关系。
- 用户确认的模块归类。
- 用户确认的特性—模块关系。
- 用户确认的基线和决策规则。
- 用户对建议的采用、驳回及原因。

AI 自己的猜测、云端搜索结论和未确认映射不得自动变成长期事实。

## 15. 本地与云端安全

### 15.1 数据分级

| 级别 | 示例 | 处理 |
|---|---|---|
| L0 绝密本地 | 项目、供应商、价格、成本、原始 BOM、用户原声 | 永不外发，不提供覆盖开关 |
| C1 公开事实 | 通用物料、公开目录型号、行业问题、公开产品规格 | 策略允许后可自动外发 |
| C2 脱敏摘要 | 不含项目身份、价格和型号的等级化特征 | 仅固定 Schema，通过检查后外发 |

“器件型号”默认是 L0。只有用户或规则库将其标记为 public_catalog 时，才能作为 C1。

### 15.2 非打断审批

建议审批分三层：

1. 首次启用云端：用户确认云端供应商、允许的 C1 字段和审计规则。
2. C1 常规请求：满足固定 Schema 时自动执行，不弹窗；结果中始终可查看实际外发。
3. C2 或无法分类：进入待审批中心，当前本地任务继续执行并标记“缺少云端证据”，不能卡住整个会话。

授权按“供应商 + 能力 + 字段级别”保存，可随时撤销。不按每一个物料反复审批。

L0 命中时直接拒绝并说明命中的字段，不进入待审批队列。

### 15.3 审计分离

设置 → 安全中心分为三个页面：

- 本地 AI 记录：问题摘要、所用本地工具、数据版本、模型、耗时。
- 云端外发记录：供应商、时间、实际 Payload、字段级别、审批依据、响应来源。
- 写入记录：写了什么、变更前后值、确认人、可否撤销。

“本地模型读数据库”不能被标成云端外发；“云端返回公开资料”也不能混入本地工具轨迹。

### 15.4 唯一网络出口

所有外部 AI 和搜索请求必须通过 Rust 侧单一网关：

- HTTPS。
- 域名白名单。
- 禁止自动重定向到非白名单域名。
- 限制请求体和响应体。
- 网关再次执行敏感字段扫描。
- 记录发送后的精确 Payload Hash。
- API Key 不进入前端日志和模型上下文。

前端组件、AI 工具和第三方库不得自行 fetch 外部地址。

### 15.5 业务沙箱

CostHub 需要的是业务工具沙箱，不是通用编码沙箱：

- 只暴露白名单业务工具。
- 只允许工具内部执行参数化数据库查询。
- 写工具生成预览 Diff。
- 文件工具只读取用户主动选择的 Excel/PPT 模板。
- 不提供 Shell、任意路径浏览、任意 SQL 和任意 URL。

## 17. 视觉与交互规范

### 17.1 整体方向

保留当前 CostHub 清冷、专业的视觉基因，收敛主题复杂度，强调数据密度、层级和可读性。无需重做品牌或引入新 UI 库。

### 17.2 布局

- 默认 1400×860 下，左侧导航约 200–220px。
- AI 面板默认收起为图标或窄条；展开宽度 380–440px。
- 全屏 AI 与侧栏 AI 是同一个组件和状态，不重新挂载会话。
- 项目工作区在 AI 收起时获得完整宽度。
- 表格和图表优先自适应内容区，而不是写死像素。

### 17.3 文字溢出

建立全局而不是逐页打补丁：

- 所有 Flex 和 Grid 子容器默认 min-width: 0。
- 表格主要字段允许两行换行；型号、编号可单行省略。
- 省略文本必须有 Tooltip 或展开。
- 卡片标题不因按钮挤压而消失。
- 标签使用最大宽度和省略。
- 数据表在窄窗口使用水平滚动，禁止压缩到字符竖排。
- 金额使用等宽数字和统一小数位。

### 17.4 反馈

- 用户动作 100ms 内出现视觉反馈。
- AI 长任务持续显示阶段、已用数据、当前工具和可中止按钮。
- 后台任务不使用成功 Toast 刷屏。
- 错误消息说明“什么失败、哪些结果仍有效、如何继续”。
- 导入和写入必须显示成功数量、跳过数量、失败数量。

### 17.5 动效

- 动效只用于状态变化、层级进入和数据更新。
- 尊重 reduced motion。
- 关闭动效不能把 Ant Design 弹窗和下拉菜单的 transition 压缩到异常状态。
- 图表初次加载不超过约 300ms；频繁刷新不重复播放入场动画。

### 17.6 可访问性

- 不只用红绿表达好坏，同时显示符号和文字。
- 键盘可操作核心表格、弹窗和确认。
- 焦点样式清晰。
- 小字号正文不低于 12px，关键数据不低于 14px。

## 19. 性能与稳定性

### 19.1 当前基线

2026-09-03 本地验证：

- 41 个测试文件通过。
- 306 个测试通过。
- 前端构建通过。
- 主包约 1.56MB minified，约 508KB gzip。
- Decomposition、AI 报告、PDF、XLSX 等为明显重包。
- 若干模块同时被静态和动态导入，导致懒加载无效。

### 19.2 优先处理

1. 先修复静态/动态混合导入，让现有懒加载真正生效。
2. Excel、PPT、PDF、OCR 和深度分析只在用户进入对应流程时加载。
3. Projects.tsx 按五个工作区拆出页面组件，但保留同一数据访问层。
4. AiPanel.tsx 拆成会话壳、事件流、结果卡和审批卡，不引入新的全局状态库。
5. 后台巡视使用单队列和扫描游标，避免重复加载全库。
6. 对 100–200 行 BOM 优先使用现有表格分页和 memo，不引入虚拟化库；只有实测卡顿再增加。

### 19.3 稳定性

- 所有冻结和批量导入操作使用事务。
- 写入失败不得留下半个版本。
- 数据库锁继续复用现有重试机制。
- 应用退出时保存前台任务状态；模型推理可中止，不假装恢复 token 流。
- 每次版本升级前自动备份数据库。

## 20. 免安装方案

继续使用免安装 exe，推荐发布为一个版本目录：

- CostHub.exe
- data/monitor_cost.db
- data/backups/
- logs/
- README.txt

影响与处理：

- 优点：复制即可使用，不需要管理员权限。
- 风险：若放在 Program Files、只读目录或 U 盘，数据库可能无法写入。
- 规则：首次启动检测目录可写；不可写时明确提示选择数据目录。
- 升级：新版本 exe 不覆盖 data 目录。
- 备份：每次 Schema 升级前自动复制数据库；保留最近 10 份。
- WebView2：优先使用系统运行时；缺失时给出清晰安装提示，不静默失败。
- API Key：便携模式仍使用 Windows Credential Manager 或系统安全存储，不写进同目录明文配置。

当前单人阶段不做自动更新服务。版本页提供“检查数据库兼容性、导出备份、打开数据目录”即可。

## 22. 分阶段实施路线

每个阶段完成后都应可独立发布。Luna 一次只执行一个小票，不同时改数据库、导航、AI 和图表。

### 阶段 0：稳定现状与规则收口

目标：先解决最影响信任的问题，不新增业务页面。

任务：

1. 建立发布前数据库备份。
2. 修复全局文字溢出基础样式。
3. 分离本地 AI、云端外发、写入三类审计视图。
4. 给 ai_advisor_insights 增加 issue_key 和 evidence_fingerprint，修复重复提醒根因。
5. 用户任务优先于后台巡视。
6. 修复无效动态导入。
7. 停止项目 BOM 导入按型号匹配后直接覆盖 parts.cost。
8. 建立目标计算、报价差异、价格来源和外发安全的最小回归测试。

验收：

- 同一证据连续扫描 10 次只提醒一次。
- 忽略后证据不变不再出现，证据变化后可重开。
- 本地分析页面明确显示“未外发”。
- 导入 A 项目 BOM 不改变 B 项目和器件主档中的价格事实。
- 核心页面在三种尺寸下无文字不可见。
- 现有全部测试和构建通过。

不做：新导航、新目标算法、新数据模型。

### 阶段 1：单一应用壳和项目工作区

目标：解决功能重复和空间挤压。

任务：

1. 一级导航收敛为五项。
2. 移除独立 AI 一级入口，侧栏和全屏复用同一组件与会话。
3. 项目详情收敛为五个工作区。
4. 建立单一归属的深链跳转。
5. 今日工作台改为待办、风险和机会。

验收：

- 同一 AI 会话在侧栏和全屏之间无丢失、无重复。
- 每项业务功能只有一个可编辑主页面。
- Dashboard 卡片只跳转，不复制编辑能力。

不做：修改业务算法。

### 阶段 2：跨品类规格与版本底座

目标：让显示器以外的产品进入同一体系。

任务：

1. 增加 category_spec_fields 和 project_spec_values。
2. 提供显示器、手写笔、鼠标、包、Dock 的初始模板。
3. 复用 project_spec_baselines 冻结规格版本。
4. 增加 BOM 版本头和版本行。
5. 给 BOM 行增加 cost_layer，统一标准成本口径。
6. 当前 project_boms 保持编辑态，冻结时复制。
7. 将原声和手账的项目字符串迁移为 project_id。
8. 模块库改为从项目 BOM 派生，停止新增 module_items。

验收：

- 同一项目主档可管理多个 SKU 规格差异。
- 旧项目显示器字段迁移后无损。
- 冻结版本后继续编辑不会改变历史。
- 物料、包装、ODM 加工费和平台费可勾稽到标准成本总计。
- 项目改名后，原声和手账关联不丢失。

不做：自动识别任意 Excel。

### 阶段 3：Charter 估算与变更包

目标：建立项目早期最有价值的成本估算能力。

任务：

1. 创建参考项目选择和相似度说明。
2. 增加变更包和变更行。
3. 实现规则成本桥和估算区间。
4. AI 只建议替换依赖组，用户拖拽确认。
5. 冻结 Charter 估算。

验收：

- 面板替换可包含 IC 和周边料依赖。
- 变更包金额之和与整机桥接差异一致。
- 缺价格项不被当作 0。

### 阶段 4：科学目标分解与价值取舍

目标：替换当前不合理的声量分摊。

任务：

1. 增加基线决策和目标版本。
2. 实现调整后基线与机会池分解。
3. 目标不可行时显示未覆盖缺口。
4. 原声增加来源、去重和人工 Kano 分类。
5. 卖点、规格、模块关系采用拖拽确认。
6. 实现成本长城图。

验收：

- 用户声量不参与正式金额分配。
- 领域目标均可回到基线和机会。
- 一个竞品的规格柱和成本曲线共用零线，正负含义正确。

### 阶段 5：报价、招标与 Open BOM 闭环

目标：让 2–3 家 ODM、2–3 轮报价真正可比较。

任务：

1. 完善导入预览和事务写入。
2. 区分价格、数量、增删、替换和规格变化。
3. 生成分供应商谈价清单。
4. CDCP 前完成定点记录。
5. 中标 Open BOM 建立冻结版本。

验收：

- 轮次差异分项之和等于总差异。
- 文件重复导入可识别。
- 规格变化不会被误判为纯降价。

### 阶段 6：量产巡视与降本闭环

目标：让自动工作真正产生不重复的成本机会。

任务：

1. 实现五类优先规则。
2. 改成事件触发 + 类别轮换。
3. 将机会一键转为措施或谈价项。
4. 区分预测和已实现降本。
5. 记录建议被采用或驳回的原因。

验收：

- 无新问题时后台安静。
- 新项目更低价能映射到量产项目。
- 已实现降本均有价格或 BOM 版本证据。

### 阶段 7：阶段成本包与复盘

目标：替代手工维护的 CDCP PPT 数据。

任务：

1. 建立单一阶段成本包模板。
2. 输出上一代对比、成本桥、目标、供应商和措施。
3. PDCP/ADCP 复用模板。
4. 复盘记录设计、商务、规格和竞争四类贡献。
5. 成果和手账引用同一 artifact。

验收：

- CDCP 数据齐全后 30 分钟内完成可用材料。
- 报告金额与页面一致。
- 过期结果在导出前可见。

## 24. 关键验收场景

### 场景 A：显示器 Charter

- 选择上一代 27 英寸项目。
- 新项目升级面板并导致 IC 和周边料变化。
- AI 建议一个替换变更包。
- 用户调整依赖项并确认。
- 系统生成成本区间、成本桥和缺失信息。
- 输入财务目标后，以确认机会池生成领域目标。

通过标准：任何金额都能回到旧 BOM、新器件估价或人工 should-cost。

### 场景 B：三家 ODM 三轮报价

- 同一规格导入三家首轮报价。
- 第二轮其中一家变更规格，另外两家纯降价。
- 系统正确区分规格变化和价格变化。
- 用户形成各供应商谈价清单。
- CDCP 前记录中标成本。

通过标准：每轮差异闭合，规格变化不被记作商务降本。

### 场景 C：成本长城

- 选择一个竞品。
- 竞品面板规格更好且面板成本更高。
- 对应柱和成本点均在正区。
- 我方某规格更好且成本更低时，对应柱和成本点均在负区。

通过标准：点击维度可看到原始规格、归一规则和成本映射。

### 场景 D：巡视去重

- 同一高价物料连续触发多次扫描。
- 只出现一次提醒。
- 用户忽略。
- 历史基线更新但结论未变，仅更新卡片。
- 新报价使影响跨越严重档位，问题重新提醒。

通过标准：提醒规则可由 issue_key 和 evidence_fingerprint 自动测试。

### 场景 E：云端研究

- 用户询问公开面板行情。
- 系统只发送公开通用名或公开目录型号。
- 本地项目、供应商、价格和 BOM 不出现在 Payload。
- 已授权 C1 查询不弹阻断确认。
- 结果返回后由本地模型结合本地成本分析。

通过标准：云端审计能展示实际外发文本，L0 自动化测试全部拒绝。

### 场景 F：CDCP 成本包

- 项目已有中标、当前 BOM、上一代、目标和措施。
- 一键生成成本包。
- 页面数字、图表和 PPT 一致。
- 源 BOM 更新后，旧成本包显示“数据已过期”。

## 27. 最终产品判断

CostHub 的差异化不在于“AI 能聊”，而在于它能把成本经理头脑中的隐性判断变成一条可追溯、可冻结、可复盘的项目成本链：

上一代与市场证据  
→ 规格和架构变更  
→ Charter 成本区间  
→ 用户价值取舍  
→ 领域目标与机会  
→ 多家 ODM 多轮报价  
→ CDCP 前定点  
→ Open BOM 与试制变更  
→ 最终 BOM  
→ 量产后行情和谈价  
→ 已实现降本与复盘

应用的优先级应始终是：

1. 数字可信。
2. 过程可追溯。
3. 任务不重复。
4. AI 不打断。
5. 视觉一眼能判断。

只要这五点成立，CostHub 才是成本领域 Agent；否则只是把若干页面和一个大模型放在了一起。
