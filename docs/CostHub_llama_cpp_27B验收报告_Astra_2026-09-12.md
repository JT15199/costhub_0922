## 需要返修的问题

### P1-1：断流错误到达 Pi 后，被上层当作正常答案返回

位置：`src/ai/piHarness.ts:62`、`src/ai/piRuntime.ts:403`、`src/components/AiPanel.tsx:839`。

复现：传输先返回“未完成的半句”，随后报告“连接中断，未收到结束标记”。真实 Pi 最终消息已带 `stopReason: error` 和 `errorMessage`，但 `runPiAgent` 正常 resolve，`finalText` 仍是该半句。Host 根据 Promise resolve 标 completed；UI 根据正文是否以“模型调用失败”开头判断完成，无法识别该错误。

影响：Rust 虽然识别了 EOF 错误，用户仍会看到正常完成；预算超限等经过相同 error message 路径的失败也需要排查。工具已经写入时，不能通过重跑整个任务处理这种失败。

最小修复：Host/runtime 检查终态，向调用者显式传播 error/aborted；保留原始部分输出供查看，但不能标成功或自动补答掩盖断流。当前复现检查以抛出明确错误为验收；若选择结构化终态，需同时更新 UI 与断言，不能只删断言。

### P1-2：多工作表读取直接塞入超大结果，后续模型无法继续

位置：`src/ai/piRuntime.ts:111-132`，对照同文件 `prepareToolResult`。

复现：真实 XLSX 编解码构造 5 张工作表，每张 450 行、20 列；调用实际 Pi `read` 默认读取。虽然每张只取 200 行，合计返回 **499,868 字符**。生产预算估算为 **240,518 tokens**，32K 模型允许输入仅 **21,954 tokens**。这里是应用估算值，不是服务端 tokenizer 实测。

原因：限制是“每张表 200 行”，没有全局字节/字符预算；该原生工具没有复用业务工具的长结果落盘。单个巨大工具交互也无法靠既有压缩可靠解决。

最小修复：默认先返回工作表清单或单表有界预览；全局控制本次结果体积，复用全文落盘及续读。测试应覆盖真实工作簿、尾部 401 行、宽表、多工作表，证明后续请求仍在预算内。不要再降低模型上下文/输出上限来掩盖问题。

### P1-3：工作表选择仅实现了 execute，没有暴露给模型

位置：`src/ai/piRuntime.ts:111-126`。

复现：从真实 `runPiAgent` 注册工具中取出 read，其 schema 只有 `path/offset/limit`，没有 `sheet`。offset 描述仍是普通文本的“1-indexed”，Excel 实现却按 0 起点切片。

影响：模型不知道可选择工作表，无法可靠只读指定表；分页语义也冲突。

最小修复：在复用 read 时补齐真实 schema 和说明，明确文本与 Excel 的 offset 语义；用模型实际收到的 schema 验证，而不只测试内部函数接受 args.sheet。

### P1-4：业务工具失败仍返回 ok:true

位置：`src/aiTools.ts:754`、`src/aiTools.ts:1106`。同文件还有多个“未找到”字符串返回分支。

复现：确认过的 `import_bom_to_project` 调用，项目代号不存在，返回 `{ ok: true, text: '未找到项目代号：DOES-NOT-EXIST' }`。

影响：工具卡和 Pi tool result 被标成功，模型需要猜中文字符串才能纠正调用。该状态会削弱失败修正及结果核对。

最小修复：检查非结构化工具的失败返回，改成明确失败/抛错，通过共用执行层传递到 Pi 和 UI。不要用正则猜全部业务字符串。真实未写入、部分写入和全部写入的回执应明确区分。

### P1-5：公司电脑的“独立样例验收”没有验收实际链路

位置：`src/ai/piCapability.ts:12-22`、`src/components/LocalBackendSettings.tsx:80`。

证据：按钮同步调用纯函数，内部 Array.from → slice → flat → reduce → map.length。没有模型调用、真实 read、业务比较、导出文件或回读；即使断网、无模型，或上述生产 Excel 读取完全失效，仍显示“长表分页、尾部异常、合计、比较和导出行数均通过”。新增单测只是断言该纯函数返回 true。

最小修复：用独立任务目录中的合成 Excel 走实际读/分页/比较/导出路径并回读核对；若保留纯函数，只能标“样例算法检查”，不能作为业务验收凭证。现有两行工具探针可保留为协议自检，两者范围必须明确。

### P2-1：自检时“取消自检”按钮不能点击

位置：`src/components/LocalBackendSettings.tsx:88`。

代码确认：运行探针时该按钮同时设置 `loading=true`。项目当前 Ant Design `node_modules/antd/es/button/button.js:179-185` 会在 innerLoading 时直接 return，不执行 onClick。取消分支因此不可达，只能等待超时或离开组件。

最小修复：取消按钮保持可点击，loading 指示独立呈现。补一次正在请求时点击取消、停止请求、再次自检的组件/桌面验证。本轮未进行真实窗口点击，此项依据组件与依赖实际实现判定。

### P2-2：托管服务端口与客户端地址分离，可能检查错服务

位置：`src/components/LocalBackendSettings.tsx:49-65` 及端口输入。

代码确认：serverConfig.port 改为 8081，只用于启动进程；健康检查仍请求 baseUrl（例如 8080）。若旧 8080 服务存在，会将其成功响应当作新进程就绪；否则新进程正常也会报告失败。切换后端还保留旧 model，能力结果也未在所有地址/模型变化时清除。

最小修复：托管模式启动、健康检查和后续聊天使用同一地址；模型/地址变化立即清除过期能力，并校验当前选择属于新端点。健康状态以当前探测返回值决定，避免读取闭包里的旧 health。验证非默认端口及两个端口同时存在的情况。

### P2-3：诊断导出不满足脱敏约定

位置：`src/components/LocalBackendSettings.tsx:75-77`。

代码确认：直接导出原始 model 和 capability.reason。当前真实 `/v1/models` 的 ID 就是 Windows 绝对模型路径，因此会把本机路径写进所谓脱敏诊断；错误原因也没有字段级净化，导出前没有显示所含字段。

最小修复：模型标识转换为不含目录的展示名/稳定摘要，错误输出限定类别与清理后的短描述；诊断预览说明字段。业务数据、原始模板、绝对路径不应混入默认诊断。
