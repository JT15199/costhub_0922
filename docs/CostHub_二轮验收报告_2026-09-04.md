## 仍需优先处理

### 1. 云端请求的“内容哈希”不是批准内容的约束

证据：[lib.rs](<D:/AI coding folder/costhub/src-tauri/src/lib.rs:986>)、[发送前临时计算哈希](<D:/AI coding folder/costhub/src/trendService.ts:277>)、[授权生成](<D:/AI coding folder/costhub/src/db/ai.ts:13>)。

新逻辑正确增加了数据库查票，但 `request_hash` 是调用方在发送时对当前正文自行计算的，后端只是再次计算并比较，没有与批准时保存的实际请求内容进行比较。修改正文后重新计算哈希仍满足这项校验。方法、目标 URL、查询参数、请求头也没有被该哈希约束；GET 空正文的哈希固定。

C1 数据库授权仍只绑定主题三字段；旧的正文关键词检查和 URL 主题包含检查仍在。普通前端又可以直接写授权表，所以尚未形成独立可信的授权签发边界。C2 的一次性使用也没有在后端原子消费。

因此，不能把“已新增 request_hash”和“已查库”直接记为安全项全部完成。这是代码层信任边界缺陷，不代表已经确认发生泄露。

修复选择：由可信后端按已批准主题构造受限字段请求，或者批准时绑定规范化请求并在发送前校验。不要用发送时自报的哈希代替批准范围。补充撤销、重放、正文/URL 篡改和合法请求的无网络回归测试。

### 2. 量产巡视实际上仍被过滤掉

证据：[autoAdvisor.ts](<D:/AI coding folder/costhub/src/autoAdvisor.ts:303>)、[项目类型枚举](<D:/AI coding folder/costhub/src/constants.ts:26>)。

过滤从“只取在研”改成了“排除已完成”，但当前合法项目类型只有“在研”和“已完成”，对现有正常数据基本没有扩大范围。项目即使阶段为“量产后降本”，只要类型是“已完成”，仍不加载 BOM 和措施。只有此类项目时直接返回。

应按生命周期阶段和是否仍需维护成本决定巡视范围，区分量产维护与真正归档，不用开发完成状态替代成本管理结束。

### 3. 目标分配通过清空机会止错，尚未达到原目标

证据：[architecture.ts](<D:/AI coding folder/costhub/src/db/architecture.ts:210>)。

当前对所有领域构造 `opportunities = 0`，所以所有分配额恒为零，目标直接等于已确认基线。这一保守处理比重复扣减正确，也能显示未覆盖缺口，但不能称为已实现“按尚未计入基线的可执行机会分配挑战”。

需保留已经计入基线的优化与尚未计入的机会之间的区别，把真实且人工确认的后者接入分配；没有证据时继续留缺口，不硬凑目标。

### 4. 原声和成本包的主要断点尚未修改

证据：[ValueTradeoffPanel.tsx](<D:/AI coding folder/costhub/src/components/ValueTradeoffPanel.tsx:25>)、[CostPackageButton.tsx](<D:/AI coding folder/costhub/src/components/CostPackageButton.tsx:40>)。

原声：导入后仅重新读取主题，没有生成主题操作；旧分析页面仍不能通过原有入口到达。选择一个模块就传 `confirmed=true`，不代表用户完成了整项确认。

成本包：“上一代与当前方案”仍只有当前规格和快照数量，“成本桥”仍只有总成本与费率；没有读取上代版本做真正对比，草稿内容与冻结来源标签也未完全分离。

应优先复用旧原声分析能力接入项目工作区，并完成用户明确要求的 CDCP 上代对比与后续措施交付，不继续扩展辅助图表。

### 5. 审批到期仍会出现“前面说允许，后面拒绝”

证据：[cloudConfirm.tsx](<D:/AI coding folder/costhub/src/cloudConfirm.tsx:227>)。

数据库找不到有效授权后，preview 分支仍可被 `confirmedKeys` 放行；没有重新进入待审批队列。离线替身已复现这个状态。虽然实际发送函数又查库能拒绝请求，但用户只会遇到任务失败，不会得到正确的下一步入口。

到期或撤销应同步清理内存票，重新给出明确审批状态。公开型号仍被统一禁止的规则也未替换为受控允许路径。
