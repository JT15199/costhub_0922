## 必须先修复的事项

### P1-01 目标分解重复使用同一笔降本机会

位置：[architecture.ts](<D:/AI coding folder/costhub/src/db/architecture.ts:118>)、[创建目标版本](<D:/AI coding folder/costhub/src/db/architecture.ts:211>)。

`buildTargetDomainRows` 先把当前成本降至已确认基线，同时把差额记为机会；`createProjectTargetVersion` 再从这个已经降低的基线上减去机会分配额。相同空间被使用两次。

已复现：当前成本 100，已确认可达基线 80，财务目标 70，平台费 0。系统返回领域目标 70、未覆盖缺口 0；实际上现有证据只支持降 20，还缺 10。

修复方向：明确“调整后起点成本”“已计入起点的降本”“尚未计入的可执行机会”，避免重复计算。机会不足时保留未覆盖缺口，不能强行给出可达成目标。另外，目标冻结目前没有整体事务，旧目标先作废、新目标后分行写入；应保证失败时旧版本仍有效。

验收：上述样例缺口应为 10；费用口径一致；无机会、机会不足、缺价、数据库写入失败均有可预期结果。

### P1-02 冻结 Charter 估算保存了参考 BOM，而非当前方案

位置：[architecture.ts](<D:/AI coding folder/costhub/src/db/architecture.ts:140>)、[CostPlanningWorkspace.tsx](<D:/AI coding folder/costhub/src/components/CostPlanningWorkspace.tsx:81>)。

选择参考项目后，`charter_estimate` 分支直接用参考冻结行覆盖当前项目 BOM。已确认变更包也没有在此计算中应用。

已复现：参考冻结 BOM 为 100，当前新设计为 150，点击相应冻结逻辑保存的总额和器件行仍是参考的 100。

修复方向：冻结用户正在评估的最终方案；参考版本保留为来源，不替换结果。变更包究竟用于形成方案还是仅解释方案，需要明确一种口径并贯彻，防止漏应用或重复应用。

验收：旧屏及关联器件换为新屏、IC 和周边料后，冻结行、显示总额和成本桥一致；更改参考项目后已冻结结果不变。

### P1-03 巡视同时存在误报和漏报

位置：[autoAdvisor.ts](<D:/AI coding folder/costhub/src/autoAdvisor.ts:162>)、[基线查询](<D:/AI coding folder/costhub/src/autoAdvisor.ts:318>)、[基线写入](<D:/AI coding folder/costhub/src/db/parts.ts:142>)。

三条相互独立的问题：

1. 跨项目比价比较的是单价乘数量，不是单价。虚构样例中，两个项目同一物料单价均为 5、用量分别为 1 和 4，被报成 5 与 20 的价格差异；没有校验必须来自不同项目。
2. 器件库确认基线写入 `baseline_type='material'`、`scope_key='part:ID'`；巡视读取 `baseline_type='part'`，候选查找又用名称与型号拼接键。这条实际入口写入的数据无法被正确消费。
3. `runAutoAdvisor` 只加载在研项目，没有在研项目时直接返回。量产项目的项目级价格和措施无法完整进入用户要求的量产后降本巡视。

修复方向：统一物料标识及基线口径；先比较单位、规格、币种等条件可比的单价，再按用量计算影响额；分别纳入在研和量产扫描范围。

验收：同价异用量不报；同规格异单价报；人工确认的基线能被读到；只存在量产项目时仍能巡视。已有相同证据去重值得保留，但应补“问题消失后关闭”“轻微变化不重新打扰”的测试。

### P1-04 云端网关未真正核验授权记录

位置：[lib.rs](<D:/AI coding folder/costhub/src-tauri/src/lib.rs:888>)、[实际外发入口](<D:/AI coding folder/costhub/src-tauri/src/lib.rs:1152>)、[授权撤销](<D:/AI coding folder/costhub/src/db/ai.ts:33>)。

Rust 校验依赖请求调用者传入的 `reviewed`、正数 `grant_id`、到期时间和哈希，没有查询实际授权记录是否存在、已撤销、作用域匹配。C1 哈希绑定的是主题三字段，不是实际请求内容；正文仅检查少量敏感字段名，URL 查询参数没有同等敏感检查。

这不表示已经发生泄露，但意味着前端错误或受污染调用不能被后端可靠阻断，不符合“最终出口独立审查”的要求。域名白名单、HTTPS、禁止重定向、C2 请求体哈希等已有保护应保留。

修复方向：由可信后端持有并核验授权，绑定规范化后的实际外发请求与受限字段；校验撤销、有效期、作用域及使用次数；模型和普通前端调用不能自签通行证。

验收：不存在的授权、已撤销授权、过期授权、篡改正文、篡改 URL 参数、复用单次授权都必须在网络发送前失败；有效公开查询可以通过。用本地测试替身验证，不发真实敏感数据。

## 流程与体验缺口

### P2-01 成本长城用整机差异填充未映射维度

位置：[CostWallPanel.tsx](<D:/AI coding folder/costhub/src/components/CostWallPanel.tsx:77>)。

未配置支撑模块时，每个维度都使用完整整机成本。整机相差 100，会在多个规格维度各画一个 100 的点，容易把总差额误读成该特性的成本差额。页面虽有提示，也不应在图中作这种替代。未评分又被当作 0，缺失与相同混为一谈。

修复与验收：未映射成本显示缺口或断点，整机差异单独展示；未评分保留未知态；共享模块清楚标注非独立归因、不可相加。一个竞品、双向规格柱和成本线的总体结构可以保留。

### P2-02 原声导入后的主题分析入口丢失

位置：[ValueTradeoffPanel.tsx](<D:/AI coding folder/costhub/src/components/ValueTradeoffPanel.tsx:25>)、[App.tsx](<D:/AI coding folder/costhub/src/App.tsx:47>)、[原有分析实现](<D:/AI coding folder/costhub/src/pages/UserVoice.tsx:104>)。

新面板只导入评论并读取已有主题，没有执行主题生成的入口；原来包含分析逻辑的 `userVoice` 页面已被路由别名重定向到项目。AI 工具提示用户去旧页面分析，也没有接上新入口。已有主题数据可能掩盖这个新用户流程断点。

此外，选择一个模块或改变一个下拉项就将主题标记为已确认，即使 Kano、决策、理由尚未完整。

修复与验收：迁移并复用已有主题分析逻辑至项目工作区，不再新造第二套分析页面；完成“导入—生成主题—查看原句—归类—显式确认—成本取舍”一次完整流程。缺字段不得悄悄成为已确认。

### P2-03 阶段成本包还不是要求的 CDCP 交付物

位置：[CostPackageButton.tsx](<D:/AI coding folder/costhub/src/components/CostPackageButton.tsx:40>)。

“上一代与当前方案”章节只列当前规格和版本数，没有读取上代 BOM、规格或差额；“成本桥”只列总成本与费率，没有展示新旧差异形成过程。领域章节只有目标参数，没有完整实际成本与达成情况。

导出前版本信息只随项目 ID 加载，当前项目刚冻结新版本后可能仍引用旧数据；即使正文使用当前草稿，成果来源仍写入最近冻结版本 ID，必须区分。

修复与验收：固定上代/当前两版来源，生成领域差额及设计、商务、规格变化归因，关联后续措施与责任人；导出前刷新数据，来源必须与正文一致。缺失证据明确留空，不用章节标题代替内容。

### P2-04 资料库深链接不能可靠切到目标标签

位置：[App.tsx](<D:/AI coding folder/costhub/src/App.tsx:361>)、[Library.tsx](<D:/AI coding folder/costhub/src/pages/Library.tsx:12>)。

导航通过 localStorage 指定资料库子页，但 Library 仅在首次挂载读取；页面又被保留挂载。先访问竞品，再从其他页面搜索器件并跳转，仍可能停留在竞品标签。情报页已增加事件响应，资料库没有对应处理。

修复与验收：子页选择使用同一明确路由状态或统一事件；首次进入和已挂载情况下，器件、模块、供应商、竞品深链接都定位到正确页及对象。

### P2-05 新增供应商看板的单一来源口径不正确

位置：[SupplierManagement.tsx](<D:/AI coding folder/costhub/src/pages/SupplierManagement.tsx:391>)。

单一来源按全部关系条数计算，没有过滤已停用供应商。一家启用、一家停用会被认作多来源；仅一家停用也会被认作单一来源。当前分母含无供应商的器件，容易淡化覆盖不足。

修复与验收：区分无有效来源、单一有效来源、多个有效来源，并去重供应商；按当前有效关系计算。ODM 语境中也应明确这只是掌握的报价/供应关系，不自动等同于供应商实际采购的唯一来源。

### P2-06 审批去重改善了，但授权过期与公开型号体验仍有缺口

位置：[cloudConfirm.tsx](<D:/AI coding folder/costhub/src/cloudConfirm.tsx:202>)、[security.ts](<D:/AI coding folder/costhub/src/ai/security.ts:25>)。

队列按物料与品类去重、跳过持久化 30 天，是有效改善。但默认 preview 模式中，数据库找不到有效授权后，`confirmedKeys` 仍可让请求返回允许，并保留旧的过期票，随后被后端拒绝，而不是重新给出清晰审批入口。

公开型号与规格仍被统一正则及后端数字规则拦截，没有用户已经同意的“公开器件型号可以外发”的受控路径。

修复与验收：到期时清理会话缓存、恢复明确待审批状态；建立小而明确的公开字段允许范围，不靠全面关闭审查解决。测试同主题授权到期、撤销、重启及合法公开型号查询。

## 新增功能与已有功能的取舍建议

- 保留并完善供应商看板、模板下载、成本长城项目级配置、待确认队列去重；它们与实际工作有关。
- 供应商地理地图可作为辅助资料展示，不建议在核心计算和闭环未修复前继续扩展。地域位置不能代替可比报价或供货能力结论。
- 继续落实唯一维护入口，但不能只删除导航：原声主题分析就是入口合并后能力未迁入的反例。旧能力先接通，再移除死代码。
- 项目页仍有 `return <CostPlanningWorkspace ...>` 后不可达的旧目标分析代码，应在行为对齐后删除，避免 Luna 以后修改到实际不会运行的旧实现。
- Charter 的“低位/高位”目前只是参考和当前成本的 min/max，不是基于新产品不确定项的估价区间。短期可改称“参考成本/当前估算”；若保留区间名称，需要给出上下界形成依据。
- 构建仍有大分包警告：主包约 1.24 MB、供应商管理约 638 KB。先处理决策正确性，不为消除警告再引入一套复杂架构。

## 建议给 Luna 的修复顺序

1. 先完成 P1-01 至 P1-04，并将上述最小反例纳入回归测试。
2. 接通原声、成本长城、阶段成本包三条完整业务流程，优先复用现有实现。
3. 修复深链接、供应商指标与审批到期行为；统一空值、缺证据和已确认状态。
4. 在独立测试数据副本上执行一条真实旅程：Charter 估算 → 替换变更 → 领域目标 → 多轮报价 → CDCP 版本与成本包 → 量产巡视 → 措施关闭。
5. 再补做桌面视觉、125%/150% 缩放、长文字、流式输出、取消/恢复及本地—云端协作验收。

通过标准不是“页面都有、测试全绿”，而是关键数字可复算、版本与证据一致、缺口不会伪装成结论、被拒绝的请求不会外发、同一问题不会无意义地反复打扰。
